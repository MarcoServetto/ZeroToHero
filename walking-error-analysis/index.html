Walking levels: the error-context corner case

Unofficial analysis, published from the marcoautomation2 fork of ZeroToHero. Not affiliated with, and not merged into, the upstream project.

This page reviews the "Walking" minigame in ZeroToHero: a series of levels where the player highlights a span of text inside a code snippet and classifies it as one of Parameter, MethodCall, ObjectLiteral, MethodDeclaration, TypeDeclaration, Type, Comment or Error. Every walking puzzle lives in ZeroToHero/src/levels/day01/Walking1.java, Walking2.java, WalkingBack.java, day03/WalkingBoomerangParam.java, day03/WalkingExplainClimb.java, day04/WalkingToForest.java and day05/WalkingHomeAlive.java, and all of them run on the same engine, ZeroToHero/src/htmlMangle/Walking.java plus ZeroToHero/src/resources/walking/Walking.js.

The mechanism

Each question stores four things: the full text, the highlighted character, the exact start/end of the "correct" selection, and the required option. The checker in Walking.js is:

const isCorrectAnswer= option=>{
 const isErrorType= requiredOption === 8;
 return option === requiredOption && (isErrorType || isCorrectSelection());
};

Two different leniencies live in this game, and they should not be confused with each other:

  • Error-answer leniency. When the required option is Error, the exact selection does not matter, only the button pressed does. This is not the corner case under discussion here: it is a deliberate, and reasonable, simplification for "something here is broken, point at roughly the right thing and say so."
  • Local-validity-despite-broken-neighbor leniency. This is the actual corner case: a puzzle whose correct answer is not Error, even though the text outside the selected span, if it had to parse on its own, would not be valid Fearless and is not written as a comment either. The player is expected to find "the smallest self-contained syntactic unit around the highlighted character" and judge only that unit, ignoring genuinely broken material sitting right next to it.

How many puzzles use the corner case, and where

Across all 7 Walking files (55 questions total), exactly 3 questions rely on the local-validity-despite-broken-neighbor corner case:

File / questionSelected unitWhat is broken nearby
Walking1.java, question 7 (of 13) //Ok, if you answered all correct, the → Comment The snippet ends with a bare +%/--%-- line, outside the comment, with no // in front of it.
Walking1.java, question 8 (of 13) //Why the question before was a → Comment Same trailing bare +%/--%-- line. This question is the one that explicitly tells the player the rule: "Error outside the smallest valid syntactical unit do not impact the answer."
day03/WalkingExplainClimb.java, question 3 (of 12) North.turn → MethodCall The whole surrounding sentence ("As we have seen, operations move forward into results. For example ` ... ` becomes `East.turn` that becomes `South`.") is plain narrative English text with backticks, never wrapped in // or /* */.

That is it: 3 out of 55, all in day 1 and day 3, and two of the three are the pair that explains the rule to the player in the same breath. Everywhere else in the Walking levels, story text that is not meant to be code is always wrapped in a real comment, so there is nothing broken left outside the selection for the leniency to matter. The corner case is real, but it is small and, in 2 of its 3 uses, it teaches itself.

Why it exists

The Walking levels are a hybrid: they are a text adventure whose narration and whose Fearless code share one text box. Two honest ways exist to keep code and story apart: keep every non-code sentence inside // (which the levels do almost everywhere), or accept that, once in a while, a line of dialogue slips through without a comment marker and let the puzzle still be gradeable. What the corner case actually teaches is exactly what a real editor's error-recovery parser does: find the nearest well-formed node around the cursor and reason about it, even though the file as a whole does not parse. That is a genuine, transferable skill, not an artifact of the puzzle format.

The other, undisclosed corner case: top level vs method body

Fearless's own parser treats "top level" and "inside a method body" as different grammars: FearlessFrontend/src/fearlessParser/Parser.java has a dedicated checkCommonTopLevelIssues pass and a dedicated topLevelNotATypeDeclaration error, precisely because a bare expression that is fine inside a method body (East, North.turn, 1 + 2) is rejected at the top level, where only type declarations are allowed. The Walking levels never tell the player which of the two grammars is in force for a given puzzle; they simply pick whichever reading makes their intended answer correct.

Concretely, at least 8 of the 55 questions only make sense once the player silently assumes "this snippet is inside a method body": North and East classified as ObjectLiteral with nothing around them (Walking1 question 4, Walking2 question 1, WalkingExplainClimb question 5), the three this.turn.turn / this.turn questions in WalkingBack.java (this has no meaning at the top level at all), the chained South.turn.turn.turn questions at the end of Walking2.java, and the bare Hungry ++ ++ / Famished++ ++ questions in WalkingHomeAlive.java. Meanwhile most of the day03-day05 puzzles wrap the same kind of content in a real top-level type declaration (Boomerang: { .throw(dir: Direction): Direction -> dir.reverse }) and so are unambiguous either way. The two styles are mixed in the same pool of questions with no marker distinguishing them.

What other similar setups do

Three patterns recur in tools that face the same problem, of a snippet whose meaning depends on an invisible frame:

  • Fix one frame and always assume it. Language playgrounds that accept a bare snippet (Try Haskell's ghci-style prompt, most "paste a Rust expression" playgrounds) do not let the ambiguity travel with the snippet: they wrap every submission in the same fixed shell (an implicit main, an implicit REPL statement) every single time, and document that choice once, up front. The user never has to guess which grammar applies to the fragment they see; the tool has already decided, permanently, and told them so.
  • Make the frame visible in the UI, not just in the grammar. Editors that support both "module" and "script" modes for the same language (for instance a playground with an explicit "wrap in body" toggle) put the choice in a visible control next to the code, rather than folding it invisibly into what counts as a correct answer.
  • Side-step single-answer classification altogether. Regex Crossword avoids the entire "is this reading valid" problem by making the puzzle a constraint satisfaction (the same cell is checked against every clue that touches it) instead of "classify this fragment against one hidden canonical parse." Duolingo's exercise grader, similarly, is built to tolerate more than one acceptable surface form rather than asserting there is exactly one correct reading of what the learner typed.

None of these tools solve the problem by asking the learner to silently infer, per exercise, which of two valid grammars is in play. They either fix the frame once and say so, show the frame, or change the win condition so a single hidden parse is no longer required.

Recommendation

Keep the local-validity-despite-broken-neighbor corner case. It appears 3 times in 55 questions, it is not hidden (2 of the 3 uses are the questions that explain the rule), and removing it would either force every stray line of dialogue into a comment (fine, but a real constraint on future level writing, since it is already the de facto convention almost everywhere else) or throw away a small, genuine lesson about local error recovery. Simplifying it away buys almost nothing: there are only 3 instances to begin with, and it would still be necessary to explain the "smallest self-contained unit" rule that the corner case exists to demonstrate. If anything, tighten the convention: every future Walking question whose surrounding text is not code should either be a real // comment or, if it is meant to be graded as broken, an Error question, so the count stays this small on purpose rather than by accident.

Do not keep the undisclosed top-level-vs-method-body switch. Unlike the first corner case, this one is not explained anywhere in the game, is used more often (at least 8 questions), and has no in-puzzle payoff: the player is never told there are two grammars, so they cannot learn the distinction, they can only guess which one the author had in mind. The fix costs nothing structurally, since the grading code does not care which frame was assumed, only the surrounding prose does. Concretely: pick one fixed default for the Walking game and say so once, in the introduction of the first level, in the same direct style already used for the error-leniency rule ("in these puzzles, code is always the inside of a method body, unless it is written as Name: { ... }, which is valid on its own"). Then bring the outliers in line with that stated rule: the bare North / East / this.turn.turn / Hungry ++ ++ questions already read naturally as "inside a method body" and need no rewrite once the rule is stated; only the framing sentence is missing, not the puzzles themselves. This is the same move every playground in the research above makes: fix the frame, then disclose it, rather than leaving two valid readings and picking whichever one is convenient for that day's puzzle.
