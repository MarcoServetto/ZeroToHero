Task (using a sub agent on fable max)

The eclipse integration is going well, now for the first non trivial part.
A little bit of autocompletion.
The idea is to rely on the compiled information instead of some very hard incremental compiler.
Note how even Java support is often failing when it comes to complex lambdas etc; as soon as the code is not fully perfect we get a mess.
So I'm thinking that reling on the last compiled version plus heuristics would help a lot; core consideration is that fearless do not allow any kind of shadowing ever, so if we can recognize a root of a sequence of method calls we are kind of sorted; two kinds of root exists:
parameterName.m1...mn
and
TypeName.m1..mn
Note also how we do not have overloading (mostly, sadly some on the receiver RC but hopefully we can 'ignore it'
The idea is that we do not need to 'check the code is correct'
we need to follow the chain of the last compiled version from type to m1 ret type...mn ret type, when we can select the right ret type if there is overloading on method arity.

Generic inference is a problem:

a.flow.map{x->x.foo}
makes it quite hard to guess the type of x. This code shape is 'for experts' in Java, but it is the bread and butter of fearless.
Often in the form
a.flow.map{::.foo}
Making it even a little harder to track the receiver.

This type propagation should be ignoring modifiers and just focus on the nominal types to be able to produce method completion, just in the sense of showing the set of allowed methods.

Ideally, when pressing . the plugin would capture enough information to guess the type of the thing before the dot and produce the list of those methods (including operator looking methods that do not start with dot)
The goal here is to give contextual support on what the user may want to write, not to make the actual autocompletion, so it is more like 'autosuggestion' showing reasonable options.

There may be the need to rewrite a simplified subset of the fearless type system, and a superset of fearless syntax inside the eclipse plugin to support all of this.

Btw. since Eclipse does not notice on-disk edits under the linked src, we could make sure that every second or so we trigger a refresh, possibly of only one of the projects to limit the impact?

Report:
Design-only task, nothing committed or changed in any repository. Proposal:
use the compiler's existing per-package JSON API cache
(.fearless_out/<pkg>.json / baseCache/base.json) as ground truth instead of
an incremental compiler - it is fully qualified, keyed by (type name,
arity), with inheritance already resolved; the <pkg>.txt rendering is
unsuitable as ground truth (aliased names, anonymous types hidden) but fits
as the doc text of a selected suggestion. Proposed engine: a small
dependency-free Java package (recommended home Controllers/src/suggest/,
so TestAllController covers it) that tokenizes with TokenKind-style
regexes, groups brackets tolerantly, parses the atom-then-postfix chain
mirroring Fearless's real left-to-right single-atom-argument grammar, and
resolves each step's nominal type using only the compiled info; roots are
parameters (found via a scope-aware binder search exploiting Fearless's
no-shadowing rule) or type names (via the package's alias table); arity
picks the right overload since Fearless has no overloading except
receiver-class (RC) overloads, which are unioned into a superset rather
than guessed. For generic inference through a.flow.map{x->x.foo} and
a.flow.map{::.foo} style chains: the lambda's expected parameter type comes
from unifying the other arguments of the enclosing call against its
declared signature, and its body is resolved the same way, feeding back
into the call's own generic return type; this degrades gracefully (shows a
superset or nothing, never a wrong answer) for type variables, {} literals
and explicit call type-args, left as later refinements. Validated with a
throwaway Python prototype against real StandardLibrary code: package
test, 4953 real call sites, a suggestion list shown 98% of the time and

Delegated task: "System restrictions" (Fable 5.1, high)`:
Now that we have more object capabilities and more methods in the System,
we should start to offer common ways to restrict those.
The core idea is that System, CapTry and all the others are non sealed interfaces, so a user can make their own implementation, capturing a more powerful capability and blocking some actions.
Iconic use cases:
ErrorCapability (ErrorCapTry for example)
Each capability offers a singleton implementation implementing all the methods with a non deterministic error.

UpdatableCapability (find better name from object capability literature)
This allows to wrap a Var[T] where T is a capability into a T that just delegates all to that Var.
Then, by for example updating that Var with the ErrorCapability, we can have a Retractable capability (is this the name?)
By starting with the ErrorCapability we can have a capability that can be enabled later.
This allows for 'deterministic capability composition'.
Consider some code wanting to restrict System.
F[mut System,mut System] would do it,
but it would be able to also call methods on the mut System. in turn making running this function non determinist.
If the provided System is a UpdatableCapability started with ErrorSystem,
then the function will be deterministic (even if started with a mut object; look to the design document of Flows to understand better how those properties work)
Now we can compose F[mut System,mut System] and only 'fill' the real system in the end.
This should be designed to work as a general API, but it should also allow for those two features:
- The manager should have some way to discover (or a package some way to expose) top level types implementing F[mut System,mut System] designed to limit the power of the initial system.
- The manager should offer ways, fearless project by fearless project, to combine those limiters/watchdogs (better name plz) in any order and to apply those limitations to any Main.
- A main of a project should be able (via a new method of System or a new object capability produced by a new method of System) to launch another main of the same project (and wait until that main completes before continuing),
and this new main should start with the same limits imposed on the caller main (so there is no recovery of capability) plus other composition this caller main choses.
for example
  sys.process.start(SecondMain,OtherFSysSys)
where
  OtherFSysSys:F[mut System,mut System]{...}
and this would be equivalent of running the new main as follow in a separated process:
```
Block#
  .var s={ErrorSystem}
  .let u={Updatable#s}//better name!
  .let ss={OtherFSysSys#(currentFSysSys#(u))}
  .do{s.set(realSys)}
  .return {SecondMain.main(realSys)}
```
Note that this must mean there is a way in the backend (invisible to fearless code) to pass either the currentFSysSys or the list of accumulated functions for recomposition in place. There could be many layers.

Then, as a second step, we could have a 
  sys.process.sideStart(SecondMain,OtherFSysSys)//better name
to immediately start the process, but not wait for the end, allowing stuff like proper actual timeout termination that would be 'transparent' from the point of view of OS interaction (that is, it would 'feel' completely as if it was in the same process.
Then, as a third step, we could have some way to pass imm objects from one process to the other and vice versa for a 'return type'.
Info errors could be easily serialized back and forth.
Another important point of discussion is 'Action'. Should any of those process method return an action instead of 'just doing it'? probably, but we need to design details. 

As you can see, this is a big design task, with a lot of open ended options.
Take your time, this is an overnight task you can research and think all you need.
You may conclude we need to talk more in a direct chat.
You may propose a partial solution.
You may chose to explain why this is a terrible idea.
You may just find it easy and implement it.
Eventually, I think I want to write a paper about it,
having object capabilities propagate via deterministic reconstruction across OS process boundaries seems a novel and very useful idea that we should develop more.

Note how this is only for a main calling another main (or possibly any lambda) on the SAME project. All the code is compiled at the same time and the manager keeps it all in sync. This pattern would not apply over multiple projects, even if handled by the same manager, since they could have a different current implementation for the same 'pkName.FunName' restriction function.
Open the needed PRs to report your findings and ideas, so that I can discuss more with another agent tomorrow.
