Task (using a sub agent on fable max)

The eclipse integration is going well, now for the first non trivial part.
A little bit of autocompletion.
The idea is to rely on the compiled information instead of some very hard incremental compiler.
Note how even Java support is often failing when it comes to complex lambdas etc; as soon as the code is not fully perfect we get a mess.
So I'm thinking that reling on the last compiled version plus heuristics would help a lot; core consideration is that fearless do not allow any kind of shadowing ever, so if we can recognize a root of a sequence of method calls we are kind of sorted; two kinds of root exists:
parameterName.m1...mn
and
TypeName.m1..mn
Note also how we do not have overloading (mostly, sadly some on the receiver RC but hopefully we can 'ignore it'
The idea is that we do not need to 'check the code is correct'
we need to follow the chain of the last compiled version from type to m1 ret type...mn ret type, when we can select the right ret type if there is overloading on method arity.

Generic inference is a problem:

a.flow.map{x->x.foo}
makes it quite hard to guess the type of x. This code shape is 'for experts' in Java, but it is the bread and butter of fearless.
Often in the form
a.flow.map{::.foo}
Making it even a little harder to track the receiver.

This type propagation should be ignoring modifiers and just focus on the nominal types to be able to produce method completion, just in the sense of showing the set of allowed methods.

Ideally, when pressing . the plugin would capture enough information to guess the type of the thing before the dot and produce the list of those methods (including operator looking methods that do not start with dot)
The goal here is to give contextual support on what the user may want to write, not to make the actual autocompletion, so it is more like 'autosuggestion' showing reasonable options.

There may be the need to rewrite a simplified subset of the fearless type system, and a superset of fearless syntax inside the eclipse plugin to support all of this.

Btw. since Eclipse does not notice on-disk edits under the linked src, we could make sure that every second or so we trigger a refresh, possibly of only one of the projects to limit the impact?

Report:
Design-only task, nothing committed or changed in any repository. Proposal:
use the compiler's existing per-package JSON API cache
(.fearless_out/<pkg>.json / baseCache/base.json) as ground truth instead of
an incremental compiler - it is fully qualified, keyed by (type name,
arity), with inheritance already resolved; the <pkg>.txt rendering is
unsuitable as ground truth (aliased names, anonymous types hidden) but fits
as the doc text of a selected suggestion. Proposed engine: a small
dependency-free Java package (recommended home Controllers/src/suggest/,
so TestAllController covers it) that tokenizes with TokenKind-style
regexes, groups brackets tolerantly, parses the atom-then-postfix chain
mirroring Fearless's real left-to-right single-atom-argument grammar, and
resolves each step's nominal type using only the compiled info; roots are
parameters (found via a scope-aware binder search exploiting Fearless's
no-shadowing rule) or type names (via the package's alias table); arity
picks the right overload since Fearless has no overloading except
receiver-class (RC) overloads, which are unioned into a superset rather
than guessed. For generic inference through a.flow.map{x->x.foo} and
a.flow.map{::.foo} style chains: the lambda's expected parameter type comes
from unifying the other arguments of the enclosing call against its
declared signature, and its body is resolved the same way, feeding back
into the call's own generic return type; this degrades gracefully (shows a
superset or nothing, never a wrong answer) for type variables, {} literals
and explicit call type-args, left as later refinements. Validated with a

A sub-agent read the OpenWith/Shortcut spec against the real Controllers,
Frontend/typeSystem, Commons and StandardLibrary/base code and found five
concrete problems: (1) the "add an association" step would call
FileAssociations.reconcile (Commons), whose contract replaces an identity's
whole extension list atomically; since one manager binary tracks every
project in one Registry, compiling project B could silently wipe project
A's associations unless the union across all projects is recomputed on
every compile - the spec does not say this; (2) the Shortcut file-naming
rule asks to invert the asset "twist" (AutoloadHandler.standardTypeName),
but that forward mapping is demonstrably lossy - foo_bar.png and
fooBar.png in the same folder both produce type name FooBar, today only
caught as a collision error - so no true inverse exists to reuse; (3)
checking that an icon is "square, appropriate size" is asked of Frontend
code that does zero file I/O, and the spec does not say whether that
check's real home is Coordinator instead; (4) a new PNG-based
AutoloadedIcon would collide with the existing base.ImageFile autoload
that five real integration-test assets already depend on, with no stated
coexistence rule; (5) smaller ambiguities - whether Shortcut should extend
OpenWith, an undefined "extension format", an inconsistent info-file
hand-edit policy (mains are user-editable today, associations would not
be), and an autopicked extension that could still collide with a
non-Fearless program's registered extension.
