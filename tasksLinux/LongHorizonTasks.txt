Task "StandardLibraryGuiCleanUp":
You are the outer agent; the sub agents you start are the inner agents.
Run at most one inner agent at a time. Every agent should be Opus 5.5 high.
Inner agents write no logs; this task overrides the global rule on sub agent logs.
Every inner agent starts in a fresh environment, with no trace of the activity of earlier inner agents.
The code of this task is StandardLibrary/base/gui and StandardLibrary/rt/gui.

The instructions for the sub agents can be sightly twisted to avoid repeated problems; but we need to keep so that if 5 runs provide unacceptable or repeated improvements we do stop, thus telling the sub agent was has been already refused is no go. If the sub agent inner randomness keeps hitting already explored ideas/areas that can not/should not be explored, we end.

The full tests are:
- TestAllFrontendCoordinatorIntegration.java;
- DeployPortableFearless.java, then, for every GUI project in StandardLibrary/integrationTests
  (testGui1, testGui2, testGuiImg, testTicTacToe, testBasketball, and any new one),
  run the portable binary on the project folder and use it as a user would, driving it
  with Controllers/src/agentTools (Pilot) as /data/gym/gui_gym.txt describes: click every
  widget, type into every text field, resize the window, and compare screenshots with
  what the program should show.
The full tests run at least once every hour, whoever is working: the outer agent
keeps the time of the last run and runs them before any step when more than an hour
has passed, and every inner agent that edits code runs them whenever it has worked
for more than an hour since its last run, and again before it replies.

1. Copy base/gui and rt/gui of the branch into a new empty folder <folder> in your
   scratchpad (as <folder>/base and <folder>/rt), without any git data, together with
   Frontend/FearlessFrontend/src (as <folder>/reference).
   Start an inner agent:
   """Read only files inside <folder>. Read all the code in <folder>/base and <folder>/rt:
   a GUI library written in Fearless, and the Java code it runs on.
   Find one kind of improvement: not one place, but a kind of code that can be improved
   the same way wherever it appears. Choose the category where you find the most
   valuable kind:
   - simplification: code that can be simplified; this often reduces the code size,
     a clearer shape of mostly the same size is good too.
   - consistency: the same thing done in different ways, or a family of builders or
     widgets where some members offer a method, a name or an argument order that the
     others do not. For the Java code, when <folder>/reference does the same thing,
     its way is the one to converge to.
   - bug: Fearless is all about predictability, so something being fragile or unpredictable is a bug too.
   - test coverage: GUI behavior that no test in the library checks.
   - performance: repeated work on every event or repaint, layouts growing badly
     with the number of widgets, needless copies.
   - ergonomics: write, in your head, a small realistic GUI program using the library,
     and find what is awkward: a missing convenience, boilerplate every program repeats, a surprising behaviour.
   Do not edit anything. Reply with the category, the kind, and a few places, before
   and after; for a consistency, the ways, the one to converge to and why; for a bug,
   one concrete program or sequence of user actions with the wrong result it produces."""

   proposed; a kind already in the file, even with different words, increases its count.
   If you refuse it, go back to 1. After 5 refusals in a row, stop.
