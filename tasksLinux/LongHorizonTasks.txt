Task "a data parallel region starts only after the stages before it have finished":
Repo: ZeroToHero (tasks/FlowDesign).
Read the sections "++ is a fence, and sends read or imm elements downstream", "Duplicated `mut` elements", "Modes: the type of the source enables parallelism" and "Sources and modes".
The document disagrees with itself on what mode `Seq` allows:
- "Sources and modes" says `Seq` allows only the sequential strategy.
- "++ is a fence..." says the stages after a `++` can run data parallel even in mode `Seq`, and that "it is the fence, not the types alone, that makes this sound": with two persons sharing one `mut Address`, `persons.seqFlow.map{p -> Block#(p.moveTo(p.name), p)} ++ {} .map{q -> q.address.street}.list` would race if the stages after it started before the stages before it had finished.
- The Disadvantages of "Modes: the type of the source enables parallelism" say a `mut List` of plain `mut` elements runs with the sequential strategy "until a `++`, `flatMap`, `distinct`, `actor` or `scan` makes its elements `read` or `imm`". Only `++` is right: `flatMap`, `distinct`, `actor` and `scan` send `read` or `imm` elements downstream, but they are not fences, so the stages before them may still mutate, at index j+1, a `mut` object shared with what a task after them reads at index j. `persons.seqFlow.flatMap{p -> Block#(p.moveTo(p.name), Lists#(p))}.map{q -> q.address.street}.list` is the same race as the `++` example. "Duplicated `mut` elements" already says `flatMap`, `scan` and `actor` never restore the split.
The rule the document needs, stated once in "Sources and modes" and referenced from the other sections: a data parallel region can start in mode `Seq` after a stage that sends only `read` or `imm` elements downstream, once the stages before it have finished with every element of the source. A `++` guarantees it, since it is a fence. A source of at most one element guarantees it after the stage, since the expansion of `flatMap` is finished before any element of it is sent downstream and no other source element exists; the strategy knows the size of a finished source, so this holds for an `Opt` and for a one element `List` alike.
Check with the definitions of positive and negative speculation calls that the one element case makes no speculation call, and say so in the text if it holds; if it does not hold, stop and write why in the PR as a question.
Fix the three passages, keep the style of the document (no history, present tense, the vocabulary of "Terms"), and add to "Examples" the race above and the one element case: `Opts#(xs).seqFlow.flatMap{l -> l}.map{..}.list` with `xs` a `mut List[mut Person]`, where the `map` runs data parallel.
Open the PR on MarcoServetto/ZeroToHero. Its description lists the three passages and the rule; whether the rule is the intended design is Marco's decision, write it as a question.

Task "Opt flows take no mode":
Repos: ZeroToHero (tasks/FlowDesign) and StandardLibrary. Run after the task above, on top of its branch, since the reason relies on its rule.
An `Opt` has at most one element, so every check a mode buys is vacuous for it: the identity check needs two elements at two indexes, the onlyImmCapture check guards an element against lambdas running on other elements, and the ban on positive speculation calls is about elements after the one the sequential strategy stops at. `Opts#(r).flow(ParRepr#)` would ask the user for a proof that proves nothing, and for wrapping the value in a `Repr`. The parallelism an `Opt` flow can have is after an expanding stage, and the rule of the task above gives it in mode `Seq`.
So an `Opt` offers the same flows as a `List` minus the mode: `mut .seqFlow` and `read .seqFlow` from `ToFlow`, recording `Seq`, and `imm .flow`, recording `ParImm`; no `.flow(mode)`. `Flows#` with up to 16 elements already records `Seq` for the same reason, applied to a fixed small source.
