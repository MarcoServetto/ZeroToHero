in-session task: "GuiBugHunt"
GUI in fearless: find uncontroversial bugs, improve code, compact, improve performance.
Details:
Remember to pace to not overshoot the 5 hours session limit.
For this night, aim to never go over 45% of the 5 hours session limit.

align branches.

Open a PR xxx.

Performance: Those tasks mention 'performance'. Agents are supposed to use their common sense, not just to rely on some measurements. Consider saving the 'tooling' that they will build and give them to other agents to avoid reinventing the wheel, but they should not rely too much on a tool that may have been design to measure a kind of performance not relevant in the task at hand.

Taking the screen/mouse/etc: Allowed and expected as part of gui testing.

Existing open PRs: try to ignore them and ask the other agents to ignore them too.

Then do many rounds as follows:
A: Ask a sub agent (Opus 5.5, high) to look to all the code in the fearless gui.
"
PR xxx contains some bugfixes. Do more.//only after the first round.
Find uncontroversial bugs and amend PR xxx with tests for those bugs.
Do not fix the bugs, show that they are real with tests.
If possible the test should be an automated Fearless test to add to one of the integration tests using the proper Fearless testing API.
If not possible, write a set of steps that replicate the malfunction on the desk by acting as a user.
"
when finished:
B: Ask a sub agent (Opus 5.5, high) to look at PR xxx.
"
check if those open bugs <list them> are uncontroversially obvious bugs, and amend PR xxx with bugfixes for those bugs.
Remember, the goal is to get predictable Gui behaviour identical on all OSs and distributions. Video drivers and graphic cards may sightly twist the pixels, but the OS should have no say at all in how stuff is rendered, especially when it comes to fonts.
We need to balance this with performance.
"
Then, directly, look to the fixes and decide if we are getting to a fix point, where there is no reasonable bug left.
A strong sign we should stop could be that agents start making bad trades that ruin performance or overall code structure to chase some hard or impossible target.

Then phase 2:
Do many rounds of the following:
A: Ask a sub agent (Opus 5.5, high) to look to all the code in the fearless gui.
"
PR xxx contains some bugfixes and some improvements in the code structure.
Improve the code structure. Do not add comments.
Make the code structure easier for an LLM to understand. The goal is not to make it easier for humans but for future LLMs reviews and bug hunts.
Do not try to discover new bugs. Focus on making the code more 'obviously correct'. Do not ruin performance and do not introduce new bugs.
Make a single new commit to the open PR with your improvements.
Make a single conceptually self contained improvement. This may have to touch a lot of places in the code.
"
B: Ask a sub agent (Opus 5.5, high).
"
Consider the open PR xxx and the difference made by the last commit.
Do you think this last comment is making it easier for an LLM like your to understand and review this code? Remember that
-distractions are the worst enemy
-verbosity can be a problem. Less tokens fit better in your context window. 
-too much compaction can also be a problem. We need to ride the right balance.
If you do not thing this last commit improves the situation, remove it.
Do not 'adjust it' to 'make it better'. Either this commit is in or out.
"
After each round review what is happening and decide where to stop:
For example:
-Agent B keep rejecting agent A proposal (4 turns in a row)
-Agent A has no idea how to improve, either it says it explicitly or proposes true absurdities.
-Overall the agents A,B start breaking the rules, adding bugs, losing performance etc.

This concludes Phase 2.
Them make a final round of review directly and check it is all ok (all tests pass etc).
Amend the PR with any last fixes. End of the task.
