# Gui API: the reference canvas

### Goal

A Fearless program with a Gui looks the same on every desk.
The programmer draws on a canvas of a size they choose.
What the user sees is that canvas, uniformly scaled, on any screen, any resolution, any OS scale setting.
Nothing is ever off screen, wrapped differently, or clipped because the screen is different.

Game engines work this way: the author designs on a reference resolution, the engine maps it to the screen with one uniform scale, and the leftover of a screen with a different shape is a band.
Browsers work the other way: the content adapts to the space it gets, so what is visible depends on the device.
Predictability is the Fearless priority, so the Gui follows the game model.
Layout helpers like the flow of `Pane` still exist, but they lay out inside the canvas, never against the window.

### Fearless facts the design relies on

The Gui is an object capability: `s.gui` from `mut System`.
A `Frame` is a window; its content is a tree of widgets drawn by the standard library itself, with bundled fonts and its own colors.
The desk's fonts, theme and scale setting play no part in how a Fearless Gui looks.
Button actions and mouse handlers run on the model queue, one at a time, in order.
The frame has a repaint timer (`.fps`) that runs on the toolkit thread.
`Gui.run` returns when the window is closed; the program continues after it.

### The model

Three quantities describe where a frame is drawn.
The programmer controls the first, says one thing once about the second, and only ever sees the third as an event.

1. The reference canvas: `W x H` in canvas units.
   Every length and position in the library is in canvas units: widget widths, insets, text height, painter coordinates, `panelWidth`/`panelHeight`, `mouseX`/`mouseY`.
   Each frame has its own canvas and may change it at any time.

2. The scale: screen pixels per canvas unit.
   In a window, the window is exactly the canvas: same shape, one uniform scale, the whole canvas and nothing else.
   The window opens centered on the screen, with the canvas shape, covering the given fraction of the screen area (capped so that the window fits the screen).
   The scale is computed in physical pixels, so the OS scale setting does not change what the user sees.
   After the window is open, the program has no control of where the window is or how big it is.

3. The shape imposed from outside: a user drag, a maximize, full screen.
   The program sees it only as a request to change the aspect ratio, delivered to `.onResize`.
   The program never learns where the window is on the screen.

### Fixed and dynamic

Platforms that run code the user did not choose to trust (browsers, mobile systems, wayland) all follow one principle: what tells the user WHO they are talking to, and the way OUT, is not under the program's control.
The Fearless Gui follows the same principle.
What identifies the window is fixed before the window opens: the program sets it on `Gui`, and `Gui.run` locks it for the life of the window.
What the user sees inside the canvas is dynamic: the program sets it on `Frame`, at any time.
The way out is the user's: the desk decorations or the Fearless corner (below), the close key and the Manager.

Fixed on `Gui`, each with a default, so that `s.gui.run{f -> ...}` is a complete program:

| Setting | Default | Meaning |
|---|---|---|
| `name` | `"Fearless App"` | the identity shown by the task switcher, the taskbar and the title bar; a blank name is a deterministic error |
| `icon` | the Fearless icon | the image shown by the task switcher, the taskbar and the title bar |
| `screenArea` | `0.3` | the fraction of the screen area the window opens with |
| `minArea` | `0.02` | the fraction of the screen area below which a Fearless window never shrinks |
| `fearlessDecorations` | desk decorations | the window opens with the Fearless decorations (below) |
| `fullScreen` | windowed | the window opens in full screen |
| `opacityFloor` | opaque | the lowest opacity the window can take |
| `closeKey` | `esc` | the key that asks the window to close |
| `fullScreenKey` | `f11` | the key that toggles full screen |

Dynamic on `Frame`: the subtitle, the canvas, the bands color, the opacity above the floor, the handlers, `fps` and `modelFps`, the content.

Not offered at all: the position of the window, a window always on top, raising the window or stealing the focus, a non rectangular window, the theme of the desk decorations, the choice of the screen (always the default screen).

### API

```
Gui:{
  read .screenWidth: WidthNat;
  read .screenHeight: HeightNat;
  mut .name(s: Str): mut Gui -> this.uName(s.u);
  mut .uName(UStr): mut Gui;
  mut .icon(Image): mut Gui;
  mut .screenArea(Float): mut Gui;
  mut .minArea(Float): mut Gui;
  mut .fearlessDecorations: mut Gui;
  mut .fullScreen: mut Gui;
  mut .opacityFloor(Alpha): mut Gui;
  mut .closeKey(KeyStroke): mut Gui;
  mut .fullScreenKey(KeyStroke): mut Gui;
  mut .run(mut Consumer[mut Frame]): Void;
  }
Frame: _Styled[Frame]{
  mut .title(s: Str): mut Frame -> this.uTitle(s.u);
  mut .uTitle(UStr): mut Frame;
  read .uTitle: UStr;
  mut .referenceCanvasSize(w: WidthNat, h: HeightNat): mut Frame;
  read .referenceCanvasWidth: WidthNat;
  read .referenceCanvasHeight: HeightNat;
  mut .bands(Color): mut Frame;
  mut .opacity(Alpha): mut Frame;
  mut .onResize(mut Consumer[ResizeRequest]): mut Frame;
  mut .onClose(mut MF[Void]): mut Frame;
  mut .close: Void;
  ...fps, elapsed, modelFps, content, contentB, onKey as today
  }
ResizeRequest: ScreenContext{ .aspectRatio: Float; }
ScreenContext:{
  read .elapsed: Instant;
  read .panelWidth: WidthNat;
  read .panelHeight: HeightNat;
  }
```

`Gui.run(consumer)`:
Opens the window with the settings of this `Gui`, gives the frame to the consumer, and returns when the window is closed.
The settings of this `Gui` can not change while a window is open: calling a setter then is a deterministic error.

`Gui.name`, `Frame.title`:
The title bar shows the name, then four spaces, then the subtitle set with `Frame.title`; with no subtitle it shows the name alone.
The name is the fixed part: a window can not stop looking like the program that opened it.
The subtitle is the dynamic part, for what the window shows now: a document, a level, a count.
The title bar and the task switcher are painted by the desk from one plain string, so the two parts can not differ in font; the four spaces are the only separation.

`Gui.icon(Image)`:
The image is scaled by the desk to each place it shows in.

`Gui.screenArea(Float)`:
A deterministic error is thrown unless `0 < screenArea <= 1`.
With `Gui.fullScreen` the window opens in full screen and `screenArea` is not used: the window the user gets out of full screen is the largest Fearless window that fits the work area (below).

`Gui.minArea(Float)`:
A deterministic error is thrown unless `0 < minArea`; `Gui.run` throws a deterministic error when `minArea > screenArea`.
A Fearless window never shrinks below this fraction of the screen area, however the user drags it (below).

`Gui.screenWidth`, `Gui.screenHeight`:
The resolution of the default screen, in physical pixels.
Only the capability knows the screen: a program holding a `Frame` and not the `Gui` can not recover the screen resolution.

`Gui.opacityFloor(Alpha)`, `Frame.opacity(Alpha)`:
The window opens opaque.
`Frame.opacity` sets the opacity of the whole window, corner included; below the floor is a deterministic error.
A pulsating effect ranges between the floor and opaque.
Only a Fearless window shows the opacity; a decorated window and a full screen window are painted opaque while they are such.

`Gui.closeKey(KeyStroke)`, `Frame.onClose(action)`, `Frame.close`:
The close key and the close button of the desk decorations both run the `onClose` action on the model queue, like a button action.
The default action is `{f.close}`: the window closes and `Gui.run` returns.
A program that asks "save changes?" replaces the action, shows its question inside the canvas, and calls `f.close` later or never.
The close key reaches no `onKey` handler.
Closing the window is not ending the program: the code after `Gui.run` runs.
The Manager is the way to see which programs are alive and to end one that ignores its close requests.

`Gui.fullScreen`, `Gui.fullScreenKey(KeyStroke)`:
Full screen is the full screen state of the desk, asked of the window manager as such, with no mode switch of the display.
A borderless window merely sized like the screen is not full screen: GNOME keeps it inside the work area, under the bars.
The canvas is centered both ways at the largest scale that fits; the leftover is painted with the `bands` color.
Entering full screen fires a `ResizeRequest` with the aspect ratio of the screen.
The program chooses only whether the window opens in full screen; after that, full screen is a decoration state and belongs to the user (below).
The full screen key reaches no `onKey` handler.

`Frame.referenceCanvasSize(w, h)`:
Sets the canvas.
Before the window is shown, it is the canvas the window opens with.
After, the content is laid out again in the new units and the window becomes exactly the new canvas at the current scale.
When never called, the canvas is the size the content takes on its own (the packed size), as every program without an explicit canvas gets today.

`Frame.bands(Color)`:
The color of the leftover, default black.
It shows in every state but the Fearless window, when the window and the canvas have different shapes (below).
The window is black before the first paint.

`Frame.onResize(handler)`:
Replaces the previous handler; the default handler does nothing.
The handler runs on the model queue, like a button action.
`aspectRatio` is the width of the requested shape divided by its height.
`panelWidth`/`panelHeight` of the request are the current canvas.
A handler accepts the request by changing the canvas to the requested shape with `.referenceCanvasSize`; there is no other way to accept.
A handler that leaves the canvas as it is rejects the request.

### Decorations

A window has either the desk decorations or the Fearless decorations, never neither and never both.
A window covers either the whole screen area it can take (the screen with the Fearless decorations, the work area with the desk decorations) or a part of it.
The two choices give the four states of a window:

| | whole | part |
|---|---|---|
| Fearless decorations | 1 full screen | 2 Fearless window |
| desk decorations | 3 decorated maximized | 4 decorated window |

The Gui sets the bounds of a window when it creates the window, and while the window is a Fearless window; at no other time.
The bounds of a full screen window are the screen, and the bounds of a decorated window are the desk's, maximized or not.
So the Fearless window is always exactly the canvas at some scale, and never shows bands.
The other three states show the canvas at the largest scale that fits, with bands when the window and the canvas have different shapes.
The program chooses the state the window opens in (`Gui.fearlessDecorations`, `Gui.fullScreen`); after that the state belongs to the user.
The program can not move its window, can not know where it is, can not minimize it and can not change its state: the decorations are how the user does these things, so they can never be taken away by the program.

The desk decorations are the title bar and borders of the desk: moving, resizing, minimizing, maximizing and closing work as on every window of that desk.

The Fearless decorations are the Fearless corner: a right triangle in the top left corner of the window, showing the Fearless logo.
The legs measure `min(screenHeight/16, windowHeight/4)` physical pixels, so the corner has the same size on every desk and still fits a small window.
The library paints the corner after everything else, over the canvas and over the bands; the content never covers it, and mouse events inside it reach no widget.
The corner is painted in physical pixels, with its own colors: it looks the same in every program.
The corner is a title bar reduced to a handle: very dark gray, the Fearless logo centered in it.
In a Fearless window its tip, a small square at the very corner of the window in a lighter dark gray, is the resize handle.
The pointer shows which, with the desk's own resize and move cursors.

The transitions.
Each gesture changes one of the two choices and keeps the other, except the full screen key.

| The user | Changes | Transitions |
|---|---|---|
| double clicks the corner | the decorations | 1 to 3, 2 to 4 |
| unmaximizes, so that every maximized bit clears (the button, the double click on the title bar, the desk's key) | the decorations | 3 to 1 |
| maximizes (the button, the double click on the title bar, the desk's key or gesture) | whole or part | 4 to 3, as on every desk |
| drags the title bar of a maximized window, which unmaximizes and moves on every desk | whole or part | 3 to 4, as on every desk |
| drags the corner of a full screen window | whole or part | 1 to 2, the drag going on |
| releases the corner or the tip with the pointer within a corner's size of the top left of the work area | whole or part | 2 to 1 |
| presses the full screen key | both, toward full screen | 2, 3, 4 to 1 |
| presses the full screen key in full screen | whole or part | 1 to 2 |

A transition is determined by the state it reaches and the window it leaves.
The window that is left gives its bounds to the new one: a full screen window gives the largest canvas that fits the work area, centered; any other window gives its own bounds.
A Fearless window takes those bounds as they are.
A decorated window takes those bounds as its outer bounds, with the canvas fitted inside the title bar and the borders; a decorated window coming from full screen is then maximized.
So the corner double click on a Fearless window gives a decorated window with the same bounds on screen and the same shape, and the corner double click on a full screen window gives a maximized decorated window that the title bar drag restores to the largest canvas that fits the work area.

Inside a state:
- In a Fearless window the corner drag moves the window and the tip drag resizes it from the top left with the bottom right corner fixed, both under the edge rule.
- A decorated window moves, resizes, snaps and minimizes as on every desk; a resize settles as below.
- A desk that allows an edge resize of a maximized window unmaximizes it in that direction only; the window stays in state 3 while any maximized bit is set.
- A single click on the corner does nothing.

A decorated window has no corner, so the way from state 4 to the Fearless decorations goes through full screen: the key, then the corner drag.

The edge rule.
A Fearless window never leaves the work area and the pointer never loses the corner: when a drag would push the bottom or the right edge of the window past the work area, the window shrinks instead, keeping its shape and its top left under the pointer, down to the min size (`Gui.minArea`); at the min size the window stops following the pointer.
A drag never grows the window: its size at the press is the most it can have during the drag, and the tip is the one way to grow it.
A drag past the top or the left edge of the work area is stopped at the edge.
The window has no memory: what the user sees is the whole state, and nothing from a finished drag changes the next one.

Why the loop is as it is.
Maximize keeps its meaning and its look on every desk.
Unmaximize is the desk's own gesture for "the other state of this window", and its answer, full screen, is the largest Fearless state, one gesture away from the desk's title bar; from there the corner leads to a Fearless window of any size, and to the desk decorations again.
The user learns one thing, the corner, with two gestures: drag and double click.
The trigger of unmaximize is "every maximized bit clears and the window is not iconified", never "the state becomes normal": a maximized window brought back from the taskbar becomes normal and is still maximized, and GNOME, on an edge resize of a maximized window, unmaximizes in that direction only and keeps the other bit, so the window stays decorated.
A snap to half the screen is a resize and the window stays decorated.
A desk without maximize (a tiling desk) reaches full screen by the key and the Fearless window by the corner.
On Windows and GNOME a drag of the title bar of a maximized window unmaximizes it and goes on as a move, and the toolkit reports the same unmaximize event for it as for the button; the two are told apart by what follows.
A drag restores the window only once the pointer has moved past the desk's drag threshold, so after the event the window keeps moving with the pointer; after the button, the double click or the key, the window is still.
The Gui watches the window position for a few repaint ticks after the event: still for a short period (a library constant, 100 ms in the demo) gives full screen, no such period within a longer one (266 ms in the demo) means the desk is moving the window and nothing happens.
The pointer plays no part: a user who clicks the button and moves the pointer away at once still gets full screen.
Every swap of decorations shows the new window before it disposes the old one; the restored window shows for the still period plus whatever unmaximize animation the desk plays before the event.
Full screen and the Fearless window are both undecorated, so a transition between the two keeps the native window and a drag goes on across it.
The program sees a transition only through the `ResizeRequest` it fires: the maximize carries the aspect ratio of the work area, full screen the aspect ratio of the screen; a move fires nothing, and a Fearless window, which is always the canvas at some scale, fires nothing.

A move or a resize by the corner is, for the desk, a move made by the program, not by the user.
GNOME keeps a window that the user has never moved through the window manager fully inside the work area on every move made by the program; Windows puts a window wherever a program asks.
The edge rule keeps every Fearless window inside the work area on every desk, so the two desks behave the same and the window manager never corrects a move of the corner.

Why the corner exists.
In full screen, or in a window without the desk decorations, the program paints every pixel the user sees: a program could paint a desktop, a Manager, a system prompt, and the user would have no way to tell.
The corner is the one region the program can not paint.
Its presence tells the user that this is a Fearless window; its double click gives the real desktop back, and the program can not take full screen again by itself.
The cost is the top left of a full screen canvas, which a program designer must know is not theirs.
A window with the desk decorations needs no corner: the desk's title bar is the evidence, and the desk's buttons are the way out.

### What a user resize does

The window manager resizes the window while the user drags; the Gui draws the canvas at the fitting scale with `bands` in the leftover, and fires nothing.
The drag has settled when the window size has not changed for a quiet period measured on the repaint timer (a library constant, like the warmup).
Then, if the window and the canvas have different shapes, one `ResizeRequest` with `draggedWidth/draggedHeight` is queued.
A handler that changes the canvas to the requested shape removes the bands; with the default handler the canvas is unchanged and the bands stay.
The Gui never sets the bounds of the decorated window to remove the bands.
The toolkit is not told when the desk's resize drag ends, and a user who pauses while holding the edge looks settled.
Bounds set by the toolkit while the desk is still resizing the same window make the two disagree on its size: the toolkit paints the size it set, and the desk shows its own larger window with the rest unpainted (`improved_gui_api_stale_paint.png`, next to this file, captured seconds after the release: a stale copy of the lower part of the canvas, then black).
The rule that a decorated window has the desk's bounds is the only one that needs no guess about the end of the drag.

Maximize and full screen are resizes whose shape is imposed: the request carries the aspect ratio of the work area or of the screen.
A desk that unmaximizes in one direction only (GNOME, on an edge resize of a maximized window) leaves the window maximized in the other; the window is resized like any decorated window.

Moving the window fires nothing.

### Coordinates

Mouse events report `mouseX`/`mouseY` in canvas units: the window position divided by the scale, rounded down.
A click on canvas point `(205, 85)` reports `X[+205] Y[+85]` at every window size and on every desk.
At scale 2, two screen pixels report the same canvas point.
A press on a band in full screen, or on the corner, is outside every widget and reaches no handler.
Painters draw in canvas units and are clipped to their widget, as today.

### Removed

`Gui.run(mut Consumer[mut Frame])` keeps its shape; the `Gui` setters come before it.
`Frame.title` as the whole title: it is now the subtitle after the fixed name.
`Frame.undecorated`, `Frame.decorated`, and a live `Frame.fullScreen`/`Frame.windowed`: the decorations and full screen are the user's; the program only chooses what the window opens as.
`Frame.maximized`, `Frame.location`, `Frame.locationX`, `Frame.locationY`, `Frame.fixedSize` and `Frame.resizable` in all their forms, `Frame.screenWidth`, `Frame.screenHeight`, `ScreenContext.screenWidth`, `ScreenContext.screenHeight`.
The errors about a maximized window with an explicit size or location, and about a window larger than the screen, go with them.

### Implementation notes

Every pixel of a frame is drawn by Skia into one bitmap, with one `canvas.scale` call for the OS transform.
The uniform scale multiplies into that call, the band offset translates it, and the clear color becomes the `bands` color.
The Swing components keep canvas bounds: no component ever sees the scale, so the layout managers do not change.
Mouse hit testing divides the window point by the scale and subtracts the band offset before `getDeepestComponentAt`.
Text stays sharp at every scale: glyph outlines are scaled, not pixels (hinting is already off).
Images drawn by `Graphics.image` go through the same transform.

The corner is painted on the same bitmap after the content, in physical pixels, and takes its mouse events before hit testing.
A drag of the corner sets the window bounds from the toolkit thread, computed by the edge rule from the pointer, the point of the corner that was pressed and the size at the press; the program never sees the position.
Window level key bindings fire only while a component inside the window owns the focus, and a full screen switch can leave the window focused with no focus owner: the Gui gives the focus to its drawing surface whenever the window gains focus.
A double click on the corner is a press with a click count of two.
The unmaximize arrives as a `WindowStateListener` event whose old state has a bit of `MAXIMIZED_BOTH` and whose new state has none and is not `ICONIFIED`; the Gui then compares the window location on each repaint tick, and gives full screen after the still period or gives up after the drag period.
Full screen is `GraphicsDevice.setFullScreenWindow`: `_NET_WM_STATE_FULLSCREEN` on X11, the full screen style on Windows, the presentation options on macOS; no display mode is set.
Switching between desk decorations and Fearless decorations is a new frame: the toolkit recreates the native window for a change of decorations anyway; it happens only on the user's request, so the native flicker is the user's own action; the new frame is shown before the old one is disposed, so the desk's close animation plays under the new window.
The decorated window that answers a double click on a Fearless window takes the Fearless window's bounds as its outer bounds, with the canvas fitted inside the insets; on X11 the toolkit guesses the insets before the window is mapped and corrects them after, so the decorated window can come out a few pixels taller.
The opacity goes through `setOpacity`, which the toolkit allows only on an undecorated window that is not the full screen window: that is why a decorated window and a full screen window are painted opaque.
Per-pixel translucency, which would keep the corner opaque while the content fades, is not used: under GNOME on XWayland a per-pixel translucent window that repaints continuously is shown or not at random (the window is mapped and focused, the toolkit paints into it, the compositor shows nothing and routes no clicks), reproduced with a forty line program, nine runs, three visible.
An opaque corner over a fading content would need a second, shaped window owned by the main one.
On macOS, Cmd+Q ends the process without a `windowClosing` unless the quit strategy is `CLOSE_ALL_WINDOWS`; the runtime sets it, so Cmd+Q is a close request.

The repaint tick compares the window size with the size at the previous tick.
A difference starts or continues a drag; equality for the quiet period settles it and queues the request, if the window and the canvas have different shapes.
The settle and the watch after an unmaximize are the only places where timing enters the design.
The settle decides only when the request is queued, never the bounds of a window.

### Example

```
s.gui.name("Nap").screenArea(0.3).run{f -> f
  .referenceCanvasSize(Width#520, Height#340)
  .bands(Color.deepNapBlue)
  .onResize{r -> f.referenceCanvasSize(Width#((340.0 * (r.aspectRatio)).softRound.getNat), Height#340)}
  .content{:: ...}
  }
```

This frame opens as a window with the desk decorations, titled `Nap`, covering 30% of the screen area, with a 520x340 canvas.
In full screen on a 16:9 screen the handler widens the canvas to 604x340 and there are no bands.
A frame with no `.onResize` keeps its 520x340 canvas and shows `deepNapBlue` bands in full screen.
Pressing `esc` closes it, since no `.onClose` replaced the default `{f.close}`.

### Demo

https://github.com/marcoautomation2/fearless_gui_demo is a Swing program that behaves as this document says, with a launcher for the fixed settings and a Show button; its `demo` release has a Linux and a Windows build.
What it has shown on GNOME: the canvas scaling and the mouse in canvas units, the title as name plus subtitle, the settle and request of an edge drag, the bands of a decorated window after a rejected request, the four states and every transition of the table but the one direction unmaximize (a single monitor GNOME offers no edge resize on a maximized window), the edge rule with the stop at the min size, the drop at the top left by the corner and by the tip, the title bar drag of a maximized window told apart from the unmaximize button (the drag was recognized in 266 ms, the double click gave full screen in 75 ms), the corner drag to the top left, full screen as the desk's state, the close question inside the canvas, and the desk facts above.
Its launcher logs every transition, request, desk report (shown, hidden, iconified, closed) and uncaught exception, and shows each window as the program sees it (state, bounds, showing or not, focus and who gets the keys, opacity), for the times a window seems to vanish.

What the hands-on tests on Windows and on a two monitor GNOME have taught, beyond the desk facts above:
- Windows puts a window wherever a program asks, under the taskbar and past the screen edge included; GNOME does not. The edge rule makes the two desks agree.
- A desk with a second monitor to the right lets the pointer reach the right edge of a maximized window from the other monitor, and GNOME then unmaximizes in that direction only. A maximized window is maximized while any bit is set.
- The desk reports one and the same unmaximize for the restore button and for a title bar drag; the window keeps moving after the event only in the drag.
- A Fearless window with a remembered size that grows back when dragged into room is hidden state: nothing on screen shows the remembered size. The window has no memory; the size at the press is the cap of the drag.
- A snap that looks at the window position never fires for the tip: the bottom right stays fixed and the shape is kept, so the top left of the window never reaches the top left of the work area. The snap looks at the pointer, on the release.
- Window level key bindings fire only while a component inside the window owns the focus; after a full screen switch the window was focused with no focus owner, and the close key and the full screen key did nothing. A window that ignores its close key looks like a window that can not be closed.
- A window that seems to vanish has a reason in the log: a close by the close key is the first thing to look for.
- The opacity pulse made a second monitor flicker once, not reproduced.
