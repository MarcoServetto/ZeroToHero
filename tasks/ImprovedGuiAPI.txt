Gui API: the virtual pixel space
================================

Goal
====

A Fearless program with a Gui looks the same on every desk.
The programmer draws in a virtual pixel space of a size they choose.
What the user sees is that virtual pixel space, uniformly scaled, on any screen, any resolution, any OS scale setting.
Nothing is ever off screen, wrapped differently, or clipped because the screen is different.
Nothing outside the control of Fearless decides how the Gui looks or behaves: not the OS, not the locale, not a setting of the user.
The fonts, the emoji images and the animations of the widgets are the library's own.
The pixels of an edge or of a gradient may be approximated differently on different machines.

Game engines work this way: the author designs on a reference resolution, the engine maps it to the screen with one uniform scale, and the leftover of a screen with a different shape is a band.
Browsers work the other way: the content adapts to the space it gets, so what is visible depends on the device.
Predictability is the Fearless priority, so the Gui follows the game model.
Layout helpers like the flow of Pane lay out inside the virtual pixel space, never against the window.

Fearless facts the design relies on
===================================

The Gui is an object capability: s.gui from mut System.
A Frame is a window; its content is a tree of widgets drawn by the standard library itself, with bundled fonts and its own colors.
Button actions and mouse handlers run on the model queue, one at a time, in order.
The frame has a repaint timer (.fps) that runs on the toolkit thread.

Terms
=====

    the program          the Fearless code that uses s.gui.
    the library          the standard library code that implements Gui and Frame.
    the desk             the operating system and its window manager.
    the user             the person at the screen.

    screen pixel         a physical pixel of the screen.
    work area            the screen minus the desk's bars (taskbar, panels).
    window               a rectangle on the screen, owned by the desk.
    desk border          the title bar and the borders the desk draws around a window.
    Fearless corner      a dark triangle with the Fearless icon, that the library paints
                         at the top left of a window without the desk border.
    resize handle        a small lighter square that the library paints over the top left
                         of the Fearless corner, in state 2 only.
    content area         the window minus its desk border; the whole window when it has none.
                         It is a rectangle.

    virtual pixel space  a rectangle of W x H virtual pixels, chosen by the program.
                         Every length and position the program uses is in virtual pixels.
                         The program never learns the size or the position of the window.
    picture              what the program draws in its virtual pixel space, as shown on the screen:
                         uniformly scaled to the largest size that fits the content area,
                         and centered in it.
    bands                the part of the content area that the picture does not cover.
                         They are painted with the bands color.

    ResizeRequest        the library tells the program a new desired aspect ratio:
                         the aspect ratio of a content area whose size the desk has chosen.
                         Each time the desk gives the content area a new size,
                         the library queues one ResizeRequest.
                         A ResizeRequest still waiting is replaced by the new one.
                         A size chosen by the library sends no ResizeRequest.

    compacting           compacting a window with the desk border keeps its top edge
                         and shrinks the content area to the largest rectangle
                         with the aspect ratio of the virtual pixel space that fits inside it:
                         the same amount is removed on the left and on the right,
                         or the amount is removed from the bottom.

The scale is computed in screen pixels.

Fixed and dynamic
=================

What identifies the window is fixed before the window opens: the program sets it on Gui, and Gui.run locks it for the life of the window.
What the user sees inside the picture is dynamic: the program sets it on Frame, at any time.
The way out is the user's: the desk border or the Fearless corner, the close key and the Manager.

Fixed on Gui, each with a default:

    name            the identity shown by the task switcher, the taskbar and the title bar.
                    Default "Fearless App". A blank name is a deterministic error.
    icon            the image shown by the task switcher, the taskbar and the title bar.
                    Default: the icon of the Shortcut of the running main,
                    or the Fearless icon when the main has no Shortcut.
                    Only an icon the running main preloads.
    start           the state the window opens in (below), set by one of four methods;
                    the last one called counts.
                    startAsWindow(initialArea)     state 4, a window with the desk border;
                    startMaximised                 state 3, maximized by the desk;
                    startUndecorated(initialArea)  state 2, a window with the Fearless corner;
                    startFullScreen                state 1, full screen.
                    initialArea is the fraction of the screen area the content area opens with.
                    Default: startAsWindow(0.3).
    minArea         the fraction of the screen area the picture always covers at least.
                    Default 0.02.
    opacityFloor    the lowest opacity the window can take.
                    Default: opaque.
    closeKey        the key that asks the window to close.
                    Default esc.
    fullScreenKey   the key that toggles full screen.
                    Default f11.

Dynamic on Frame: the subtitle, the virtual pixel space, the bands color, the opacity above the floor, the handlers, fps and modelFps, the content.

Not offered at all: the position of the window, a window always on top, raising the window or stealing the focus, a non rectangular window, the theme of the desk border, the choice of the screen (always the default screen).

API
===

    Gui:{
      mut .screenWidth: WidthNat;
      mut .screenHeight: HeightNat;
      mut .name(s: Str): mut Gui -> this.uName(s.u);
      mut .uName(UStr): mut Gui;
      mut .icon(ImageFile): mut Gui;
      mut .startAsWindow(initialArea: Float): mut Gui;
      mut .startMaximised: mut Gui;
      mut .startUndecorated(initialArea: Float): mut Gui;
      mut .startFullScreen: mut Gui;
      mut .minArea(Float): mut Gui;
      mut .opacityFloor(Alpha): mut Gui;
      mut .closeKey(KeyStroke): mut Gui;
      mut .fullScreenKey(KeyStroke): mut Gui;
      mut .run(mut Consumer[mut Frame]): Void;
      }
    Frame: _Styled[Frame]{
      mut .title(s: Str): mut Frame -> this.uTitle(s.u);
      mut .uTitle(UStr): mut Frame;
      read .uTitle: UStr;
      mut .virtualPixelSpace(w: WidthNat, h: HeightNat): mut Frame;
      read .virtualWidth: WidthNat;
      read .virtualHeight: HeightNat;
      mut .bands(Color): mut Frame;
      mut .opacity(Alpha): mut Frame;
      mut .onResize(mut Consumer[ResizeRequest]): mut Frame;
      mut .onClose(mut MF[Void]): mut Frame;
      mut .close: Void;
      ...fps, elapsed, modelFps, content, onKey
      }
    ResizeRequest: ScreenContext{ .aspectRatio: Float; }
    ScreenContext:{
      read .elapsed: Instant;
      read .panelWidth: WidthNat;
      read .panelHeight: HeightNat;
      }

Gui.run(consumer):
Opens the window with the settings of this Gui, gives the frame to the consumer, and returns when the window is closed.

Gui setters:
A Gui is the capability that makes windows, not a widget: each setter returns a new Gui with the new setting, and leaves the Gui it is called on unchanged.
A setter that contradicts an earlier setting of the same Gui is a deterministic error: the second of the two calls throws it, and names the setting to change first.

Gui.name, Frame.title:
The title bar shows the name, then four spaces, then the subtitle set with Frame.title; with no subtitle it shows the name alone.

Gui.icon(ImageFile):
The argument is an autoloaded image, the same value a main names in Shortcut[I] and OpenWith[I]: s.gui.icon(IconsFoo) for _pkg/icons/foo.png.
The icon is one of the icons the running main preloads; any other image is a deterministic error of Gui.icon.
A main preloads the icon I of each Shortcut[I], OpenWith[I] and PreLoadIcon[I] it implements, and base.IconsFearless.
PreLoadIcon[I] is a claim like Shortcut[I] and OpenWith[I]: only a main can implement it, and the manager accepts only a square PNG image with a side from 64 to 1024 pixels.
The compiler gives each generated main the list of its preloaded icons, so the check is the same with and without the manager.
A main implementing Shortcut[I] gives the icon I to every Gui it runs; with more than one Shortcut, the first one declared.
The title bar and the task switcher show the icon on every desk.
The desks that show the icon of an installed program instead of the icon of the window (GNOME, COSMIC, the Windows taskbar) show it for a main the manager runs: the manager installs the preloaded icons of every main (below).
A program the manager does not run shows its icon only where the desk shows the icon of the window.

Gui.startAsWindow(initialArea), Gui.startMaximised, Gui.startUndecorated(initialArea), Gui.startFullScreen:
A deterministic error is thrown unless 0 < initialArea <= 1, and when initialArea < minArea.
With startAsWindow and startUndecorated the window opens centered on the work area; its content area has the aspect ratio of the virtual pixel space and covers initialArea of the screen area, capped so that the window fits the work area.
With startMaximised the window opens with the desk border at the size of the leaving bounds of state 1, centered, and the library asks the desk to maximize it: that window is the restore size.
With startFullScreen the window opens as state 1.
On a tiling desk every start but startFullScreen opens the window as state M (below): the desk chooses its size.

Gui.minArea(Float):
A deterministic error is thrown unless 0 < minArea <= 1, and when minArea > initialArea of a startAsWindow or startUndecorated start.

Gui.screenWidth, Gui.screenHeight:
The resolution of the default screen, in screen pixels.

Gui.opacityFloor(Alpha), Frame.opacity(Alpha):
The window opens opaque.
Frame.opacity sets the opacity of the whole window, Fearless corner included; below the floor is a deterministic error.
Only state 2 shows the opacity; the other states are painted opaque while the window is in them.

Gui.closeKey(KeyStroke), Frame.onClose(action), Frame.close:
The close key and the close button of the desk border both run the onClose action on the model queue, like a button action.
The default action is {f.close}: the window closes and Gui.run returns.
The close key reaches no onKey handler.

Gui.startFullScreen, Gui.fullScreenKey(KeyStroke):
Full screen is the full screen state of the desk, asked of the window manager as such, with no mode switch of the display.
The full screen key reaches no onKey handler.

Frame.virtualPixelSpace(w, h), Frame.virtualWidth, Frame.virtualHeight:
Chooses the virtual pixel space.
Before the window is shown, the window opens with it.
After, the content is laid out again in the new virtual pixels and the window changes as the state machine says (below).
When never called, the virtual pixel space is 1000 x 1000.

Frame.bands(Color):
The color of the bands, default black.
The window is black before the first paint.

Frame.onResize(handler):
Replaces the previous handler; the default handler does nothing.
The handler runs on the model queue, like a button action.
aspectRatio is the desired aspect ratio: the width of the content area divided by its height.
panelWidth/panelHeight of the request are the current virtual pixel space.

The state machine on floating desks: Windows, macOS, GNOME, KDE Plasma, Cinnamon, MATE, Xfce, LXQt, COSMIC
==========================================================================================================

A floating desk lets windows overlap and keeps the size and the position the library sets for a window.
The floating desks are Windows, macOS, and on Linux GNOME (Ubuntu, Fedora, Debian), KDE Plasma (Kubuntu, openSUSE), Cinnamon, MATE, Xfce (Xubuntu), LXQt (Lubuntu) and COSMIC (Fedora COSMIC).
Every desk that is not a tiling desk (below) is a floating desk.

The program chooses the state the window opens in (Gui.startAsWindow, Gui.startMaximised, Gui.startUndecorated, Gui.startFullScreen); after that the state belongs to the user.

    STATES

    There is always exactly one window.
    In every state the picture covers at least minArea of the screen area.

    State 1: FullScreen
      the window has the Fearless corner.
      the window is in the desk's full screen state and covers the screen.
      the content area is the screen.
      the bands exist when the virtual pixel space and the screen
        have different aspect ratios.

    State 2: FearlessWindow
      the window has the Fearless corner and the resize handle.
      the window is inside the work area.
      the window is the picture: there are no bands.

    State 3: DeskMaximized
      the window has the desk border.
      the window is in the desk's maximized state and covers the work area.
      the bands exist when the virtual pixel space and the content area
        have different aspect ratios.
      the restore size the desk keeps is the leaving bounds of state 1, compacted:
        a size of the screen, never the size of an earlier window.

    State 4: DeskWindow
      the window has the desk border.
      the window is not maximized.
      the window is compacted: there are no bands,
        except while the desk is resizing the window.
      the restore size the desk keeps is the window itself,
        except while the desk is resizing the window.
      the desk does not shrink the window below the smallest window
        whose picture covers minArea of the screen area.


    CREATING A WINDOW

    A transition between the desk border and the Fearless corner replaces the window with a new one.
    The window after a transition takes its place from the window before it, the leaving bounds:
      leaving state 1:  the largest rectangle with the aspect ratio of the virtual pixel space
                        that fits 77% of the width and 77% of the height of the work area, centered.
      leaving state 2:  the rectangle of that window.
    Entering state 1: the desk's full screen.
    Entering state 2: the window is exactly the leaving bounds.
    Entering state 4: the leaving bounds, compacted.


    ACTIONS

    A delegation is a transition after which the same action goes on in the new state.

    Corner drag
      (press the Fearless corner, outside the resize handle, with the primary button;
       move past the desk's drag threshold; release)
      in 1:  transition to 2;
             then delegation: the same drag goes on in 2.
      in 2:  the window moves so that the pressed point of the Fearless corner
             stays under the pointer, under the edge rule.
             On release within screenHeight/16 of the top left of the work area:
               transition to 1.

    Resize handle drag
      (press the resize handle with the primary button; move past the drag threshold; release)
      in 2:  the top left of the window follows the pointer;
             the bottom right of the window stays fixed;
             the window keeps the aspect ratio of the virtual pixel space,
             under the edge rule.
             On release within screenHeight/16 of the top left of the work area:
               transition to 1.

    Corner double click
      in 1:  transition to 4.
      in 2:  transition to 4.

    Full screen key
      in 1:        transition to 2.
      in 2, 3, 4:  transition to 1.

    Desk maximize (the button, a title bar double click, a drag to the top, the desk's key)
      in 4:  transition to 3;
             the library sets the restore size to the leaving bounds of state 1, compacted.

    Desk unmaximize (the button, a title bar double click, a title bar drag, the desk's key)
      in 3:  the desk unmaximizes the window.
             Once the desk has reported a new position and size after the unmaximize
             and no pointer button is down:
               if the window is at the position of the restore size: transition to 1;
               otherwise the desk has moved it (a title bar drag, which goes on
               as the desk's move: a delegation):
               the window is in state 4, and the library compacts it.
             A snap of a maximized window is no unmaximize: the window stays maximized vertically, as a window in state 4.

    Title bar drag
      in 4:  the desk moves the window; it stays in state 4.

    Desk resize, snap
      in 4:  the desk changes the size of the window; while it does, there are bands.
             When the desk has finished, the library compacts the window
             and sets its restore size to the compacted window.
             The desk has finished when no pointer button is down:
             a desk resize by the pointer lasts as long as a button is held,
             and a desk resize by a key is finished at once.

    Desk minimize, restore from the taskbar
      in 3, 4:  the window keeps its state.

    The program chooses a new virtual pixel space
      in 1, 3:     the library computes the new bands.
      in 2, 4:     the library gives the window a new size and position
                   (in 4, while the desk is resizing the window,
                   nothing until the desk has finished).
                   The content area takes the aspect ratio of the new virtual pixel space.
                   If not all of these constraints can be respected,
                   the earlier ones in this list win:
                     1. the picture covers at least minArea of the screen area;
                     2. the four corners of the window are in the work area;
                     3. the center of the picture stays in the same place;
                     4. the content area covers the same fraction of the screen area.

    Close key, desk close button
      in every state: the program's onClose action runs.


    THE EDGE RULE (corner drag and resize handle drag, state 2)

    The window never leaves the work area.
    A drag that pushes the right or the bottom edge of the window past the work area
      shrinks the window, keeping its aspect ratio and its top left under the pointer.
    At minArea the window stops following the pointer.
    A drag past the top or the left edge of the work area stops at that edge.
    A drag never grows the window; the resize handle drag is the only way to grow it.

Why the transitions are as they are.
Maximize keeps its meaning on every desk; unmaximize, the desk's gesture for "the other state of this window", gives full screen; a title bar drag of a maximized window gives a desk window, as on every desk.
The Fearless corner moves the window between states 1 and 2, and its double click gives the desk border back.
The full screen key gives full screen from every state.
The restore size the desk keeps is the window itself in state 4 and a size of the screen in state 3, so the desk has no memory of an earlier window: what the user sees is the whole state.
A title bar drag out of state 3 gives a window of a reasonable size for the screen, whatever size the window had before the maximize.
Desks keep a restore size per window when it maximizes, tiles, snaps or zooms it, and gives it back when the user drags the window out; moving or resizing the window is not enough to replace it.
Nothing in the state machine depends on timing.

Why the library waits for the pointer buttons.
A window resized by the library while the desk is still resizing it ends with the toolkit and the desk disagreeing on its size: the window shows a stale paint.
The press and the release of a desk resize happen on the desk border, so the window receives neither.
The size staying the same for a while is no end either: a user pausing on the border looks the same.
The desk reports the same unmaximize for the button, the title bar double click, the key and the title bar drag.
The button, the double click and the key put the window at the position of the restore size; a title bar drag puts it under the pointer, wherever the pointer is.
The size does not tell the gestures apart: GNOME gives back a restore size above 80% of the work area resized to its own choice, at the same position.
Nothing in the gesture itself is visible: the title bar is the desk's, and on Wayland desks the pointer is the compositor's during the drag.
An unmaximize always changes the size of the window, so the desk always reports a new position and size; the decision waits for that report, not for a time.
GNOME 50 first puts a window dragged out of the maximized state at the position of the restore size, and moves it under the pointer after, while the button of the drag is still down: so the decision also waits for the pointer buttons, as a desk resize does.
A desk that never shows the button of its drag to the window (KDE Plasma on Wayland) puts the window under the pointer in its first report.
A title bar drag that starts exactly where the window, placed under the pointer, lands at the position of the restore size is read as a double click.

Why the Fearless corner exists.
Without the desk border the program paints every pixel the user sees, and could paint a desktop or a system prompt.
The Fearless corner is the one region the program can not paint: it tells the user that this is a Fearless window, and its double click gives the desk border back; the program can not take full screen again by itself.
The cost is the top left of the picture in states 1 and 2, which a program designer must know is not theirs.

COSMIC and KDE Plasma on Wayland tell no X11 client when a resize by their border or their keys ends.

    State 4 on COSMIC and on KDE Plasma on Wayland
      after a desk resize the bands stay: the library never compacts after a desk resize.
      the library compacts only a size it chooses itself.

On every desk, a window the desk holds at a size (a window tiled to half the screen by KDE Plasma) keeps that size after a new virtual pixel space, and shows bands.

COSMIC is a floating desk with three more differences.
COSMIC chooses the position of every window and keeps the top left of a window whose size the library sets.

    The program chooses a new virtual pixel space, on COSMIC
      in 2, 4:  the top left of the window stays where it is;
                constraint 3 (the center stays in the same place) does not apply.

    Corner drag and resize handle drag, on COSMIC
      in 2:  the drag goes on as the desk's move or the desk's resize from the top left;
             the edge rule does not apply while the desk moves the window.
             On release: the library shrinks the window so that its corners are in the work area,
             and compacts it after a resize;
             a release within screenHeight/16 of the top left of the work area is a transition to 1.
      in 1:  transition to 2; the drag does not go on.

COSMIC tells no X11 client its work area.
On COSMIC the top edge of the work area is screenHeight/30 below the top of the screen, the height of the default top panel.
The left, right and bottom edges of the work area are those of the last window COSMIC maximized.
Before any window is maximized, the bottom edge is screenHeight/14 above the bottom of the screen, the height of the default dock, and the left and right edges are those of the screen.

The state machine on tiling desks: Hyprland, sway, i3
=====================================================

A tiling desk sets the size and the position of every window: Hyprland (Omarchy), sway (Arch with sway) and i3 (Void with i3).
The library recognizes a tiling desk when XDG_CURRENT_DESKTOP names Hyprland, sway or i3, or when SWAYSOCK is set.

The program chooses whether the window opens as state 1 (Gui.startFullScreen) or as state M (any other start).
After that the state belongs to the user.

    STATES

    There is always exactly one window: a transition never replaces it.
    The state is the one the desk reports: a full screen the desk starts or ends is a transition.

    State 1: FullScreen
      the window has the Fearless corner.
      the window is in the desk's full screen state and covers the screen.
      the content area is the screen.
      the bands exist when the virtual pixel space and the screen
        have different aspect ratios.

    State M: DeskManaged
      the window has the Fearless corner, and the border the desk gives it, if any.
      the desk chooses the size and the position of the window, tiled or floating.
      the bands exist when the virtual pixel space and the content area
        have different aspect ratios.

    The window opens asking for a content area of initialArea, centered;
    the desk keeps that size only for a window it floats.
    The library never sets the size or the position of the window after it opens.


    ACTIONS

    Corner double click
      in 1:  transition to M.
      in M:  transition to 1.

    Corner drag: nothing.

    Full screen key
      in 1:  transition to M.
      in M:  transition to 1.

    Desk full screen (the desk's own key: Super+F on Omarchy)
      in 1:  transition to M.
      in M:  transition to 1.

    Desk tile, float, move, resize, swap
      in M:  the desk changes the window; a new size queues a ResizeRequest.

    The program chooses a new virtual pixel space
      in 1, M:  the library computes the new bands.

    Close key, desk close
      in every state: the program's onClose action runs.

Why a tiling desk has two states.
A tiling desk owns the size of every window: it ignores the bounds set on a tiled window, so a compaction or a move by the library changes nothing.
The desk resizes and moves windows with its own gestures (Super + drag on Hyprland), which hold the pointer, so the library can not know when a desk resize ends.
State 2 has no desk border to give back, and maximizing is the desk's business (Omarchy ignores the maximize requests of programs).
The Fearless corner is in both states, so the user always sees that the window is a Fearless window, and its double click is the one gesture that moves the window between the two states.

Coordinates
===========

Mouse handlers receive the position of the pointer in virtual pixels: the position in the content area minus the bands, divided by the scale, rounded down.
A press on a band, or on the Fearless corner, is outside every widget and reaches no handler.
Painters draw in virtual pixels and are clipped to their widget.

Layout
======

The size of a widget is state: a number for the width and one for the height, held by the widget.
It changes only when the program acts on the widget, never when the layout runs.
The layout only places widgets: a parent places each child at its size, or larger with .fill.

Sizes:

    Widget[S]:_Styled[S]{
      mut .width(n:Nat):mut S->this.width'(WidthNat#n);
      mut .width'(WidthNat):mut S;
      mut .height(n:Nat):mut S->this.height'(HeightNat#n);
      mut .height'(HeightNat):mut S;
      mut .pack:mut S;
      mut .fill:mut S;
      mut .noFill:mut S;
      read .width:WidthNat;
      read .height:HeightNat;
      read .fill:Bool;
      ...insets, radius, colors
      }

The width and the height include the insets; both start at 24.
A width smaller than leftInset+rightInset is an error at the second setter: .width 4 after .leftInset 6, or .leftInset 6 after .width 4.
The same holds for the height with topInset and bottomInset.

The last action on a widget decides its size:
  .width and .height set it;
  a new text of a Button or a Label, a new child of a Pane or a Border, grows it on each axis to fit the new content;
  the text of a TextField or a TextArea never changes its size: what does not fit scrolls;
  .pack sets it to the smallest size that fits the current content.
A new content never shrinks a widget: a shorter text leaves a Button as wide as before, until .pack.
A child added to a container grows the container to fit that child alone, plus the insets.
A child that changes after it is added does not change its parent.
In the builder the scope of a child runs before the child is added.

.pack fits all the current content with the current size of each child:
  a Button or a Label fits its text;
  a TextField or a TextArea fits its text with its scroll bars, one displayed line for each line of the text;
  a Pane fits its lines, broken only at maxPerLine: one line by default, a column with .maxPerLine 1;
  a Border fits its regions: north, the row of west, center and east, and south, one above the other.

.fill places a widget larger than its size, on the axes its parent allows: the space a Border gives its region, the space a Pane gives its line.
.noFill is the default.
.fill never changes the size of the widget: the getters return the size, and painters and mouse handlers receive the space they are drawn in as panelWidth and panelHeight.

Why a container does not grow when its children wrap.
A Pane in the north of a Border whose buttons wrap into a second row when the virtual pixel space gets narrower would take height from the center.
A horizontal change would then remove vertical space from another widget, depending on where the lines of a far away Pane break.
Instead the north keeps its height and the second row is clipped, with a warning.

Why sizes change only when the program acts.
A size computed from the children at every layout costs a walk of the tree for every widget, or a cache kept between repaints, which is the measuring loop again.
A size that is state costs nothing to read, and the program can always override it after the content is added.

Every clipping prints a warning: a widget that does not fit in its parent, a text that does not fit in its widget, a painter that draws past the edges of its widget.

Regions:
A place for one child is a region: the five regions of a Border, the two regions of a Split, the content of a Frame, the title and the content of a section.
A region is filled through a RegionFiller.
A RegionFiller has one method per kind of widget, taking the scope of that widget.
That method puts the widget in the region and returns the container of the region.

    RegionFiller[S:*]:{
      mut .pane(mut Scope[Pane]): S;
      mut .border(mut Scope[Border]): S;
      mut .split: mut RegionFiller[mut And[mut SplitWith[S]]];
      mut .sections(mut Scope[Sections]): S;
      mut .button(mut Scope[Button]): S;
      mut .label(mut Scope[Label]): S;
      mut .picture(mut Scope[Picture]): S;
      mut .textField(mut Scope[TextField]): S;
      mut .textArea(mut Scope[TextArea]): S;
      }
    Frame:{ ... mut .content: mut RegionFiller[Void]; }
    Border:_Container[Border]{ ... mut .north: mut RegionFiller[mut Border]; ...south, east, west, center }

Filling a region that holds a widget replaces that widget.
A region never filled is empty: a Frame never given a content shows an empty window.

A Pane holds any number of children, so a Pane has the same family of methods, each returning the Pane.
The kinds of widget are listed in these two types only, RegionFiller and Pane: a new kind of widget adds one method to each.
Why: one method per kind of widget per region grows with the product of the regions and the kinds; the RegionFiller keeps that product at two.

Border:
A Border has five regions: north, south, west, east and center.
The height of the north region is the height of its child, and the region spans the width of the Border; the same for south.
The width of the west region is the width of its child, and the region spans the height between north and south; the same for east.
The center region is the rest.
With .fill, the child of center fills both axes, the children of north and south fill the width, the children of west and east fill the height.
A child smaller than its region is centered in the region, on both axes.

Pane:
A Pane is .horizontal or .vertical.
It lays its children out in lines: rows for .horizontal, columns for .vertical.
The line axis runs along a line; the stack axis is the other one, where the lines stack.

    Pane:_Container[Pane]{
      mut .horizontal: mut Pane;
      mut .vertical: mut Pane;
      mut .minPerLine(Nat): mut Pane;
      mut .maxPerLine(Nat): mut Pane;
      mut .lineScroll(Bool): mut Pane;
      mut .stackScroll(Bool): mut Pane;
      mut .centered(Bool): mut Pane;
      ...children, gaps, mouse, paint
      }

A line holds at least minPerLine children (default 1) and at most maxPerLine children (default Math.maxNat).
Between the two, a child that would make the line longer than the Pane starts a new line.
A minPerLine more than the maxPerLine is an error at the second setter.
The lines break against the space the Pane is drawn in, never against a size its children report.
With .fill, a child takes the whole line axis of the Pane, and keeps its own size on the stack axis.

Placement:
centered(True), the default, centers each line on the line axis, the stack of lines on the stack axis, and each child on the stack axis of its line.
centered(False) places them at the start of each axis: the left and the top.

Scrolling:
lineScroll(True) scrolls the line axis, stackScroll(True) scrolls the stack axis; with False, what does not fit is clipped.
A scroll bar is shown whenever its setting is True, and always takes its space, also when everything fits.
Every scroll bar of the library, on a Pane, a TextField or a TextArea, is 5 virtual pixels thick; with nothing to scroll, the thumb is as long as its track and drawn in the faint color of the track, so it reads as disabled.
A press on a scroll bar scrolls and reaches no handler: on the thumb it starts a drag, on the track it moves by one view.
The wheel scrolls the innermost Pane under the pointer that scrolls on that axis and can still move; shift makes the wheel scroll sideways.
A Pane keeps its scroll position in virtual pixels when its lines break again.
Open: a program can not set the scroll position of a Pane, so it can not scroll a child into view.

Split:
A Split has two regions and a divider between them.
.horizontal (the default) puts the first region left of the second; .vertical puts the first region above the second.
The axis of a Split is the width for .horizontal and the height for .vertical.

    Split:Widget[Split]{
      mut .horizontal: mut Split;
      mut .vertical: mut Split;
      mut .dividerPosition(n:Nat): mut Split;
      read .dividerPosition: Nat;
      mut .draggable(b:Bool): mut Split;
      read .draggable: Bool;
      mut .mouse(mut Scope[Mouse]):mut Split;
      mut .paint(Painter):mut Split;
      mut .first: mut RegionFiller[mut Split];
      mut .second: mut RegionFiller[mut Split];
      }
    Pane:_Container[Pane]{ ... mut .split: mut RegionFiller[mut And[mut SplitWith[mut Pane]]]; }
    RegionFiller[S:*]:{ ... mut .split: mut RegionFiller[mut And[mut SplitWith[S]]]; }
    And[T:*]:{ mut .and: mut RegionFiller[T]; }
    SplitWith[S:*]:{ mut .with(mut Scope[Split]): S; }

    .split.pane{:: ...}.and.label{:: ...}.with{:: .vertical .dividerPosition 30}

.split fills the first region, .and the second region, and the scope of .with receives the Split with both; .with returns the container of the Split.

Every divider is 5 virtual pixels thick on the axis, as thick as a scroll bar, and spans the Split on the other axis.
A Split has no gaps: it is not a _Container, and the divider is the only space between its two regions.
The divider position is a distance in virtual pixels on the axis: from the start of the Split, after the left inset for .horizontal and after the top inset for .vertical, to the divider.
The first region goes from that start to the divider.
The second region goes from the end of the divider to the end of the Split, before the right inset or the bottom inset.
The default divider position is 0.

The divider stands at the divider position, whatever the size of the children and of the space the Split is drawn in.
A divider position past the end of the Split leaves the second region empty, and the divider is clipped.
Each region spans the Split on the other axis.
A child takes its region as the center of a Border does: with .fill it fills the region, and a child smaller than its region is centered in it.
A child larger than its region is centered on the region and clipped to it, on both sides.

The divider is drawn in the faint color of a scroll track, with a darker grip in the middle.
The user drags the divider with the mouse primary button: the divider follows the pointer, and the drag sets the divider position.
A drag keeps the divider inside the Split.
A press on the divider reaches no handler, as a press on a scroll bar.
The pointer over the divider shows the resize cursor of the axis.
.draggable is True by default.
With .draggable(False) the divider has no grip and the pointer over it shows the default cursor.
A press on that divider is a press on the Split.

A new child grows the Split as a new child grows a Pane or a Border: to fit that child alone, plus the insets.
.pack sets the length of the Split on the axis to the lengths of the two children plus the divider, plus the insets.
On the other axis, .pack sets the length of the Split to the larger of the two children, plus the insets.
.pack also sets the divider position to the length of the first child on the axis.

Why the divider stands where it is put.
The program and the user put the divider at a position, and no layout moves it: predictability wins over convenience.
The space a Split is drawn in changes only when the program acts: a new virtual pixel space, a new size of a widget.
So the program that changes that space also sets the divider position it wants in the new space, for example in its .onResize handler; the user can always drag the divider.

Open: a widget larger than the space its parent gives.
It is clipped by its parent.
It could be an error instead, in the offensive style.
Many other things clip as well (a long text in a region, a line forced by minPerLine), so clipping stays, and this point is open.

Text editing
============

A TextField holds one line of text; a TextArea holds any number of lines.

    Button:_Caption[Button]{ ... }
    Label:_Caption[Label]{ ... }

The text:
The text of a TextField has no newline: a .text or .uText with a newline on a TextField is a deterministic error.
The lines of a TextArea are its text split on newline: "a" newline has two lines, the second one empty, and the caret can stand on it.
The text holds any UStr the program gives it; what the user adds goes through .onInput first.

The offsets:
.caret and .anchor are offsets in unicode scalar values, the unit of UStr.size.
The selection is the text between .anchor and .caret; nothing is selected when they are equal.
The user moves the caret and the anchor only to the boundaries of grapheme clusters.
The program reads the caret and the anchor in a TextEvent, and has no way to set them.
A program .text or .uText erases the caret and the selection: the caret goes to the end of the new text and nothing is selected.

Incoming text:
Every text the user adds goes through .onInput before it reaches the widget: a typed text, a pasted text, a text an input method commits.
.onInput receives the incoming text and returns the text to insert; an empty result inserts nothing.
The default reduces the incoming text to Str:
  carriage return newline and carriage return become newline, tab becomes space;
  each scalar value is decomposed (NFKD), so an accented letter becomes its letter;
  what is still not in Str is dropped;
  in a TextField, newline becomes space.
A result with a newline for a TextField is a deterministic error.

Open: the keys a desk turns into text.
The program never sees the keys pressed inside a TextField or a TextArea, only the text that comes out of them.
The same keys can give a different text on another desk: a keyboard layout puts q or a on the same key, a dead key turns ´ then e into é, an input method turns nihon into 日本 after the user picks it from a list.
Each of these is the desk deciding which text the user typed, the way a paste is the clipboard deciding it, and the program receives that text through the same .onInput.
This is less predictable than the rest of the Gui, and there is no clear better rule yet.

Input methods:
The text an input method is still composing is drawn underlined at the caret; it is not part of the text and reaches no handler.
When the input method commits it, the committed text goes through .onInput like a typed text.
The library tells the input method where the caret is, so that its list of choices opens next to the caret.

Events:
Each action of the user is one model task, queued with the clicks and the keys: one key, one paste, one cut, one undo.
The task changes the text and the caret, runs .onEdit if the text changed, and the frame shows the result only when the task ends.
.onEdit runs for every change of the text the user makes, with the text after the change; a move of the caret or of the selection alone runs nothing.
A .text, .uText or .uAppend of the program never runs .onEdit or .onCommit.
The committed text is the text of the last commit or of the last .text, .uText or .uAppend of the program.
A commit runs .onCommit when the text differs from the committed text, and the text becomes the committed text.
A commit happens on Enter and on Ctrl+Enter, and when the focus leaves the widget by a press elsewhere, Tab or Shift+Tab.
A press elsewhere queues the commit first and the handlers of the press after it.
A widget removed from the window (.clear, a replaced Border region, a new .content) commits nothing.
A new .onInput, .onEdit, .onCommit or .caret replaces the earlier one.

Focus:
At most one TextField or TextArea of a frame has the focus; it receives the keys and shows the caret.
A press on a TextField or a TextArea gives it the focus and places the caret at the pressed point.
A press anywhere else in the window takes the focus away; a band and the Fearless corner are part of the window.
Tab and Shift+Tab, in the widget that has the focus, give the focus to the next and the previous TextField or TextArea of the window, in the order of the tree, from the last back to the first.
Without a widget with the focus, Tab reaches Frame.onKey like any other key.
The focus moving away and back changes nothing in a widget: the text, the caret, the selection and the scroll position stay as they are.
A widget without the focus shows no caret, and draws its selection in a muted color.
The caret is shown only while the window has the keyboard.

Keys:
While a widget has the focus, the keys below and the keys that type text are used by it and never reach Frame.onKey, whether the widget is editable or not.
Every other key reaches Frame.onKey: the function keys, Escape, Insert, and Shift, Ctrl and Alt themselves.
A key held when the focus changes sends its release where its press went.
The close key and the full screen key keep their meaning.

    Pointer
      press            focus, caret at the pressed point, nothing selected
      Shift+press      the selection extends to the pressed point
      drag             selects from the press to the pointer; past an edge it scrolls
      wheel            scrolls as on a Pane; Shift+wheel scrolls sideways
      scroll bar       as on a Pane
      right press      nothing
    Moving the caret; with Shift, each also extends the selection
      Left, Right      one grapheme cluster; without Shift, a selection collapses to its start or its end
      Up, Down         one displayed line (TextArea); in a TextField they reach Frame.onKey
      Home, End        the start and the end of the displayed line
      Ctrl+Home, Ctrl+End  the start and the end of the text
      PageUp, PageDown one view (TextArea); in a TextField they reach Frame.onKey
    Editing; nothing on a widget that is not editable
      a typed text     through .onInput, replaces the selection or goes at the caret
      Backspace        deletes the selection, else the grapheme cluster before the caret
      Delete           deletes the selection, else the grapheme cluster after the caret
      Shift+Enter      inserts a newline (TextArea); nothing in a TextField
      Ctrl+X           cuts the selection to the clipboard
      Ctrl+V           pastes the clipboard through .onInput
      Ctrl+Z           undo
      Ctrl+Y, Ctrl+Shift+Z  redo
    Always
      Ctrl+A           selects all the text
      Ctrl+C           copies the selection to the clipboard
      Enter, Ctrl+Enter  commit
      Tab, Shift+Tab   moves the focus

There are no word movements: Ctrl+Left, Ctrl+Backspace and a double click do what Left, Backspace and two clicks do.
The clipboard is the desk clipboard only, with the same keys on every desk; there is no selection pasted by the middle button.
On a widget that is not editable, the user can still focus it, move the caret, select, copy and scroll; the caret is shown.

Undo:
Each user action that changes the text is one step of the history: undo goes back one step and restores the caret and the anchor of before the step; redo goes forward.
A new change after an undo drops the steps that redo would replay.
An undo and a redo are changes the user makes: they run .onEdit.
With .textClearsUndo(True), the default, a .text, .uText or .uAppend of the program empties the history.
With .textClearsUndo(False), it is one step of the history like a user action.

Scrolling and wrapping:
A TextField always has a horizontal scroll bar.
A TextArea always has a vertical scroll bar, and a horizontal one exactly when .wrap is False.
With .wrap(True), the default, a line of the text longer than the widget goes on over more displayed lines; the breaks fall between words when a line has a break, inside a word only when the word is longer than the widget, and never change the text.
After every move of the caret by the user, the view scrolls by the least amount that shows the caret.
A .text or .uText scrolls the view to show the caret at the end.
.uAppend adds at the end, keeps the caret and the selection where they are, and moves an offset that the new text puts inside a grapheme cluster to the start of that cluster.
If the view showed the last displayed line before .uAppend, it shows the last displayed line after it; otherwise the view does not move.

The caret:
The caret painter draws the caret with its origin at the top of the caret position, clipped to the widget, every repaint tick.
.sinceMove is the time since the caret last moved or the text last changed.
The default caret is a line 2 virtual pixels wide and .lineHeight high, in the foreground color, shown for the first 500 milliseconds of every second of .sinceMove.

Why the user actions are model tasks.
A text that the toolkit changes at once and reports to the program later loses keys: a handler that sets the text from an old event overwrites what the user typed since, and the caret jumps.
Queued with the clicks and the keys, the user and the program change the text in one order.
The cost is when the model is busy: the text shows up late, as in a busy terminal.

Why Enter commits also in a TextArea.
Chat programs commit on Enter and give a newline on Shift+Enter; document editors give a newline on Enter and commit on Ctrl+Enter.
Shift+Enter is a newline and Ctrl+Enter is a commit in both, so only Enter is in question, and the shorter key goes to the commit.

The same Graphics paints a container (.paint) and an image (Image.paint).

Graphics has three kinds of settings: the color, the position and the text settings.
The color starts as the foreground of the widget, or as opaque black for an image; the position starts at (0, 0).
The text settings are .textHeight, .aboveBaseline and .belowBaseline, and start as the defaults of a Label: 12, +1.0 and +0.5.
Each drawing call uses the settings and leaves them unchanged.

Every line of text the library draws, in a widget or with Graphics, is drawn in its room.
The line box of a text is textHeight times aboveBaseline + belowBaseline high, rounded to the nearest virtual pixel, and as wide as the advance of the text.
The ink of the text may go past the line box: stacked combining marks, tall scripts, glyphs that overhang.
The room of the text is the line box, grown on each axis by twice the largest part of the ink past the line box on that axis.
The text is drawn centered in its room, so no ink is clipped.

g.textRoom(text) is the room of one line of text with the current text settings: .width, .height, and .baseline, the distance from the top of the room to the baseline, rounded to the nearest virtual pixel.
A Label with the same text and text settings packs to that room plus its insets.

g.text(text) draws one line of text in the color, in its room, with the top left corner of the room at the position.
g.text(text, width, height) draws one line of text in the color, centered in the box of width x height whose top left corner is the position, as a Label draws its text in its content box.
A box smaller than the room does not clip the text.
With the room and the box, a program aligns text as it needs: left at x, right at x - room.width, centered on a point, centered in a cell.
A decoration goes with the room: a highlight is a .rect of the room, an underline is a .line a little below room.baseline.

g.textLines(text, width) is the text broken into lines whose rooms are at most width wide, as a TextArea wraps its text.
A line break of the text ends a line.
A line breaks after a word; a word wider than width breaks between characters; a single character wider than width is a line alone.
The spaces where a line breaks are not part of the line.

g.image(image) draws the image at its own size: one pixel of the image on one virtual pixel.
g.image(image, width, height) draws the image scaled to width x height virtual pixels, with its top left corner at the position.
The image goes to the screen in one scaling step.

A program reacts to the mouse with the handlers of .mouse, one for each kind of event.
A handler takes the event as its parameters: the position of the pointer in the widget, .elapsed, and the size of the widget, as ScreenContext tells them.
On a widget with a .doubleClicked, the second click of a double click runs .doubleClicked instead of .clicked; a click after a double click is a single click again.
A click is the second click of a double click when it is of the same mouse button as the click before, pressed at most 500 milliseconds after it, and at most 4 pixels of the screen away from it.
The library decides this, not the desk.
The double click on the Fearless corner is decided in the same way.

Open: what Graphics does not offer.
Graphics draws lines one virtual pixel wide and no arcs.
The bundled fonts have one weight.
.text shapes its text at each call, and a painter runs at each repaint tick: a cache of shaped lines in the library would cost the program nothing.

Sections
========

    Pane:_Container[Pane]{ ... mut .sections(mut Scope[Sections]):mut Pane; }
    RegionFiller[S:*]:{ ... mut .sections(mut Scope[Sections]): S; }
    Sections:_Container[Sections]{
      mut .section: mut RegionFiller[mut And[mut Sections]];
      mut .tabs(Bool): mut Sections;
      mut .expand(index: Nat): mut Sections;
      mut .collapse(index: Nat): mut Sections;
      mut .remove(index: Nat): mut Sections;
      mut .title(index: Nat): mut RegionFiller[mut Sections];
      mut .content(index: Nat): mut RegionFiller[mut Sections];
      mut .onTitleClick(mut SectionHandler): mut Sections;
      mut .onClose(mut SectionHandler): mut Sections;
      read .size: Nat;
      read .isExpanded(index: Nat): Bool;
      }
    SectionHandler:{ mut #(sections: mut Sections, index: Nat): Void; }

A Sections is a list of sections.
A section has a title and a content.

Words:
A section is expanded when its content shows, and collapsed when it does not.
Expand and collapse are about the content only: the title always shows.
Close is only what the x of a title asks for: to take the section out of the list.
Remove is what the program does to take a section out of the list.

Indexes:
The index of a section is its position in the list, from 0; .size is the number of sections.
An index that is not below .size is a deterministic error, also in a handler that runs after the program removed sections.

Adding a section:
.section fills the title of a new section, .and fills its content, and filling the content adds the section at the end of the list.
.title(index) and .content(index) replace the title and the content of the section at that index; the section keeps its place in the list and stays expanded or collapsed.
A new section is collapsed.

Expanding:
At most one section is expanded: .expand collapses the expanded one.
No section expanded is a normal state.

Tabs:
.tabs(False), the default, shows the sections in a column, one under the other: each title, and under it its content when the section is expanded.
.tabs(True) shows the titles in one row, and the content of the expanded section in the space below the row.
.tabs can be called at any time, and the expanded section stays expanded.

The user:
A click on a title is a press and a release on the same title.
A click on a widget inside the title that takes clicks (a Button with an action, a widget with a .clicked or .doubleClicked handler) is a click on that widget, not on the title.
A Button with no action lets the click reach the title.
The two clicks of a double click are two clicks on the title.
A click on a title runs the handler of .onTitleClick with the index of the section, on the model queue, like a Button action.
The default handler expands the section: {s, i -> Block#(s.expand i, Void)}.
.onClose shows an x at the end of every title.
A click on the x runs the handler of .onClose with the index of the section, on the model queue; the section stays until the program removes it.
The handlers run only for clicks of the user: .expand, .collapse and .remove never run them.
A new .onTitleClick or .onClose replaces the earlier one.

A collapsed content:
A collapsed content is not drawn, takes no mouse events, and the Tab key does not move the keyboard into it.
It keeps its widgets and their state.
Collapsing a section takes the keyboard from a TextField or TextArea of its content, as removing the section does.
.remove takes the title and the content out of the window.

Layout:
The head of a section is the row of its title.
In a column, a head spans the width of the Sections inside the insets, and is as tall as its title.
The title stands after a mark 16 virtual pixels wide and a widthGap, at its own size; with .fill it takes the head up to the x.
With .onClose, the x takes the last 16 virtual pixels of the head, after a widthGap.
The content of an expanded section is under its head, after a heightGap, placed as a child in a line of a Pane: at its own size and centered, and with .fill as wide as the head.
A heightGap separates a section from the next one.
In tabs, the heads stand in one row from the left, separated by a widthGap; a head is its title at its own size and the x, and the row is as tall as the tallest title.
The content space is below the row after a heightGap, down to the bottom inset.
The expanded content takes the content space as a child takes the center of a Border: at its own size and centered, or filling it with .fill, and it is clipped to it.
A row wider than the Sections is clipped, with a warning.

The size of a Sections is state, as the size of every widget: expanding and collapsing never change it.
A new section grows the Sections to fit that section alone: its head, a heightGap and its content, plus the insets.
.pack fits all the heads and the largest content: in a column the heads, each followed by a heightGap, and the largest content; in tabs the row, a heightGap and the largest content.
A column taller than the Sections is clipped, with a warning.

Drawing:
Each head is a band in the faint color of a scroll track, darker when the section is expanded.
In a column, the mark is an arrow that points right for a collapsed section and down for an expanded one.
The mark and the x are drawn in the foreground color of the Sections.

Why the x only asks.
The program owns the list: a section leaves the list only when the program removes it.
Toolkits where the x removes the tab by itself need a second mechanism to refuse it, and an event after the tab is gone.

Why the handlers do not run for the calls of the program.
A handler that runs for the calls of the program runs in the middle of building the sections, and a handler that expands a section runs itself again.

Tooltips
========

    Widget[S]{ ...
      mut .tooltip(s:Str):mut S->this.uTooltip(s.u);
      mut .uTooltip(UStr):mut S;
      read .tooltip:Str->this.uTooltip.getStr;
      read .uTooltip:UStr;
      }

Every widget has a tooltip: a text, empty by default.
An empty tooltip shows nothing.
When the pointer rests for 500 milliseconds on a widget with a tooltip, the library shows the tooltip of the deepest widget with a tooltip under the pointer.
The pointer rests on that widget while it moves inside it, also over its children.
The tooltip hides when the pointer leaves that widget, or when a mouse button is pressed.
After a press the tooltip stays hidden until the pointer moves, and shows again when the pointer then rests for 500 milliseconds; the tooltip of a widget that replaces the widget under the pointer stays hidden as well.
The tooltip is drawn by the library inside the window, in virtual pixels, over every widget: a light box with a thin border, holding each line of the text in its room, in the bundled fonts at text height 12.
The top left corner of the box is 20 virtual pixels below the pointer; the box moves left to stay inside the content, and above the pointer when there is no room below it.
The box stays where it appeared while the pointer rests on the widget.
A new tooltip text shows at the next repaint.

Menus
=====

    Widget[S]{ ...
      mut .contextMenu(mut Scope[Menu]):mut S;
      mut .openMenu(mut Scope[Menu]):Void;
      }
    Menu:_Styled[Menu]{ .self->this;
      mut .item(mut Scope[MenuItem]):mut Menu;
      mut .separator:mut Menu;
      }
    MenuItem:_Styled[MenuItem]{ .self->this;
      mut .text(s:Str):mut MenuItem->this.uText(s.u);
      mut .uText(UStr):mut MenuItem;
      mut .enabled(Bool):mut MenuItem;
      mut .check(Bool):mut MenuItem;
      mut .radio(Bool):mut MenuItem;
      mut .action(mut MF[Void]):mut MenuItem;
      mut .submenu(mut Scope[Menu]):mut MenuItem;
      }

A menu is a column of items and separators.
The library draws it inside the window, in virtual pixels, over every widget: a light box with a thin border, each item as high as the room of its text plus 6 virtual pixels (24 for a text whose ink fits its line box), each text in the bundled fonts at text height 12.

Opening a menu:
w.openMenu(scope) builds a menu with the scope at once, and opens it below the widget w.
w must be in the open window: .openMenu before the window is open, or on a widget that is not in the window, is a deterministic error.
w.contextMenu(scope) gives w the menu that a click of the secondary mouse button opens at the pointer.
That click goes to the deepest widget with a context menu under its press that contains its release, as a click of the primary button goes to the deepest widget that takes it.
At each of those clicks the scope builds the menu as a task of the model queue, and the menu opens when the scope returns.
No widget has a context menu by default; a new .contextMenu replaces the earlier one.

The scope of a menu:
A menu exists only while it is open.
Its scope builds it each time it opens.
The items of a menu are fixed once its scope returns: a Menu or a MenuItem saved and changed later is a deterministic error.
A menu with no item, with no separator or only separators, does not open, and leaves the open menu open.

Items:
The text of an item is one line, drawn as it is: a newline in it is a deterministic error, and no character of it has a special meaning.
.enabled(False) shows the item in grey; it is never highlighted, the keys skip it, and choosing it does nothing: the menu stays open.
.check(b) shows a check box, ticked when b is True; .radio(b) shows a radio button, filled when b is True.
The library never changes a mark.
When any item of a menu has a mark, every text of that menu starts after a column for the marks.
An item has an action or a submenu, never both; it shows a check box or a radio button, never both: the second of the two setters is a deterministic error.
A new .action, .submenu, .check or .radio replaces the earlier one of the same setter.
An item with no action and no submenu closes the menus and does nothing else.
A separator is a thin line, shown exactly where the program adds it, also first, last, or next to another separator.
An item with a submenu shows an arrow on its right.

The open menus:
A frame has at most one open menu, and the submenus opened from it, one inside the other: the open menus.
Opening a menu, with .openMenu or a context menu, closes the open menus first.
Once open, a menu stays where it is until it closes.
Nothing the program does to the widgets moves it or closes it: not .clear, not a new .content, not a new virtual pixel space; the menu keeps its actions.
The open menus close when the user chooses an item without a submenu, presses outside them, or presses the close key, when the window loses the focus, and when the program opens another menu.

Where a menu opens:
A menu opens against an anchor: the widget of .openMenu, the pointer for a context menu, the item for a submenu.
A menu opens below its anchor, starting at its left edge; when it does not fit below and fits above, it opens above.
When it does not fit starting at the left edge of its anchor and fits ending at the right edge, it ends at the right edge: a context menu opens left of the pointer.
A submenu opens right of its menu, its first item beside its item; when it does not fit right and fits left, it opens left of its menu.
Then the menu moves left and up by the least amount that keeps it inside the virtual pixel space.
A menu taller than the virtual pixel space is as tall as the space and has a scroll bar on its right, drawn as the scroll bar of a Pane.
The wheel over the menu, a drag of the thumb and a press on the track scroll its items; Up and Down scroll the highlighted item into view.
A submenu opens beside the place its item has in the scrolled menu.
A menu wider than the virtual pixel space starts at its left edge, and the part outside is clipped, with a warning.

The mouse while a menu is open:
The mouse reaches only the menus: no handler of a widget runs, no Button lights up, no tooltip shows, the wheel scrolls only a menu with a scroll bar under the pointer, the pointer is the default arrow.
Moving the pointer highlights the enabled item under it.
A click of the primary button on an item chooses it: the press and the release on the same item.
A press on an item and a release on another item choose nothing.
A press of any button outside the open menus closes them all, and that press, its drag and its release reach nothing else.
The second click of a double click reaches nothing when a menu took its first click or opened after its first click.
A press of another button on a menu does nothing.

Choosing an item:
Choosing an item without a submenu closes the open menus, then queues its action on the model queue, like the action of a Button.
Choosing an item with a submenu closes the submenus opened after its menu, then its scope builds the submenu as a task of the model queue, and the submenu opens when the scope returns.
Choosing that item again while its submenu is open closes its submenu.
The item whose submenu is open is drawn highlighted in grey.
A submenu opens only when its item is chosen: never when the pointer rests on its item, never after a delay.

The keys while a menu is open:
Every key reaches only the menus: no TextField or TextArea receives a key, no Frame.onKey handler runs.
The text an input method commits reaches nothing.
Up highlights the previous enabled item of the last open menu, and Down the next one; past the last item Down goes on from the first, and past the first item Up goes on from the last.
With no item of that menu highlighted, Down highlights its first enabled item and Up its last.
Enter chooses the highlighted item of the last open menu.
The close key of the Gui closes the last open menu, and does not ask the window to close.
The full screen key keeps its meaning.
A key pressed before a menu opened sends its release to Frame.onKey as usual.
Menus bind no keys: no accelerators and no mnemonics.
A program binds keys with Frame.onKey, and a key handler can open a menu with .openMenu.

Why a menu is built when it opens.
A menu kept as a tree of items needs the program to keep each item enabled, ticked and named in step with its state; an item the program forgets shows a stale state.
Toolkits that keep the tree add a second mechanism to refresh it just before it shows, or enable items on their own by rules the program does not see.
A menu built when it opens has one source of truth, the state of the program.
A check item that ticks itself holds a second copy of the state, which disagrees with the program when the action refuses the change.
A group of radio items that untick each other needs the program to declare the group, and a forgotten group gives items that tick together.
Here the program says which items are ticked, at each opening.

Why a click, and never a press, a drag and a release.
When a press opens a menu, the release of that press lands on the item that appeared under the pointer and chooses it.
Here a menu opens on the release of a click, and an item is chosen by a whole click: no gesture both opens a menu and chooses an item.

Why a press outside the menus reaches nothing.
A press that closes a menu and also reaches the widget under it runs an action the user did not aim at: the user was aiming at the menu.
The cost is that moving from one menu of a menu bar to the next takes two clicks.
The same reason holds for the second click of a double click: a user who double clicks an item would click what is under the item once the menu closes.
And a double click of a Button that opens a menu would close the menu or open it again, depending on how fast the model ran the action.

Why nothing opens on hover.
A submenu that opens when the pointer rests on its item closes when the pointer crosses another item on its way to the submenu.
A menu bar that switches menus when the pointer moves gives a pointer move a meaning that depends on whether a menu is open.
Here only a click opens a menu, and only a press closes one.

Why the library decides the context click.
Desks open a context menu on the press of the secondary button, or on its release; a program that checks one of the two shows no menu on the other desks.
Here the context click is a whole click of the secondary button, on every desk.

Why menus bind no keys.
A menu exists only while it is open, so it can not hold a key binding.
Key bindings held by menus work only while the menu is in the window, clash silently with other bindings, and show the names of the modifiers of each desk.
Mnemonic markers take characters out of the text of an item.

Why the close key closes the last open menu.
The close key is Escape by default, the key a user presses to leave a menu: asking the window to close would end the program for the most common menu gesture.

Open: what a menu does not offer.
A menu wider than the virtual pixel space is clipped; a menu scrolls only up and down.
An item has no icon, no key hint and no tooltip.
No key opens the context menu of a widget; a program can bind a key with Frame.onKey to .openMenu.
Choosing a check item closes the menu, so ticking several items takes several openings.
The program can not close the open menus.
Left and Right do nothing in a menu; Enter opens a submenu.

Implementation notes
====================

Every pixel of a frame is drawn by Skia into one bitmap, with one canvas.scale call for the OS transform.
The uniform scale multiplies into that call, the band offset translates it, and the clear color becomes the bands color.
The Swing components keep bounds in virtual pixels: no component ever sees the scale.
Mouse hit testing divides the content area point by the scale and subtracts the band offset before getDeepestComponentAt.
Text stays sharp at every scale: glyph outlines are scaled, not pixels (hinting is already off).
Images drawn by Graphics.image go through the same transform.
TODO: the library draws with Skia on the GPU, straight into the surface of the window: Direct3D 12 on Windows, Metal on macOS, OpenGL or Vulkan on Linux.
A frame then needs no copy.
Skia in software is the fallback when no GPU device is available, and its frame reaches the window with one copy.

The Fearless corner is painted on the same bitmap after the content, in screen pixels, with legs of min(screenHeight/16, windowHeight/4), and takes its mouse events before hit testing; it answers the primary button only.
A drag of the Fearless corner sets the window bounds from the toolkit thread, computed by the edge rule from the pointer, the point of the corner that was pressed and the current size; the program never sees the position.
A drag starts past the desk's drag threshold, as a drag of a title bar does; a double click on the Fearless corner is the release of a second click: a window replaced while a button is down leaves XWayland reporting that button down until the pointer next enters one of its windows.
Window level key bindings fire only while a component inside the window owns the focus, and a full screen switch can leave the window focused with no focus owner: the library gives the focus to its drawing surface whenever the window gains focus.
Full screen is GraphicsDevice.setFullScreenWindow: _NET_WM_STATE_FULLSCREEN on X11, the full screen style on Windows, the presentation options on macOS; no display mode is set.
On Windows the runtime sets sun.java2d.d3d=false: with the Direct3D pipeline the toolkit makes full screen an exclusive mode of the display, and on a desk scaled above 100% the bounds set in the same event that leaves it reach the native window unscaled (a 600x400 window shows as 400x267 at 150%); the library paints one bitmap and gains nothing from Direct3D.
Moving between the desk border and the Fearless corner is a new frame: the toolkit recreates the native window for a change of decorations anyway; on Windows the new frame is shown before the old one is disposed, so the desk's close animation plays under the new window.
Elsewhere the old frame is disposed before the new one is shown: the toolkit answers WM_TAKE_FOCUS without XSetInputFocus when it already counts the window as focused, so under GNOME a new undecorated frame shown while the old one holds the keyboard can stay without the keyboard.
Disposing the old frame first lets the desk give the keyboard to another window of the program; the gesture that caused the change was on the desk border, so the new frame carries no newer user time, and the desk's focus stealing prevention can keep the keyboard on that other window.
So, off Windows, the library asks the desk to activate the new frame with a _NET_ACTIVE_WINDOW message whose source is a pager, the source desks obey without focus stealing prevention; it sends the message once the desk manages the new frame (WM_STATE).
The library sends its X11 client messages on the toolkit's own connection: requests on one connection reach the desk in order, so the message comes after the request that maps the frame.
The restore size is set on Windows with SetWindowPlacement: the restore rectangle in work area coordinates and device pixels, with SW_SHOWMAXIMIZED when entering state 3 and SW_SHOWNORMAL after a compaction.
SetWindowPlacement with the current rectangle also ends a snap: Windows keeps the size from before a snap as the restore size of the snapped window, and setBounds moves the window but keeps that size and the snap.
The window handle is WComponentPeer.getHWnd of the frame's peer: the runtime opens java.desktop/java.awt and java.desktop/sun.awt.windows to the library.
On X11 and macOS the library sets no restore size: the desk maximizes the window itself and keeps the window before the maximize as the restore size, so a title bar drag out of state 3 gives the window before the maximize, and a compaction is setBounds alone.
The toolkit reports a window the desk tiles to half the screen as MAXIMIZED_VERT: state 3 is exactly MAXIMIZED_BOTH.
On a tiling desk the library asks the desk for full screen with the _NET_WM_STATE client message on the X11 root window, and reads _NET_WM_STATE_FULLSCREEN on the window at each repaint tick: the state is what the desk did, never what the library asked.
A window that opens as state 1 sends the message once the desk manages the window, which the desk marks with the WM_STATE property: a message sent before is ignored, and a _NET_WM_STATE set before mapping does not survive the mapping.
sway and i3 report a tiled window as maximized; on a tiling desk the maximized state has no meaning.
The X11 window managers of Wayland desks (Hyprland, wlroots, Smithay for COSMIC) set no _NET_FRAME_EXTENTS and no _NET_WM_ALLOWED_ACTIONS, on floating and tiling desks alike: nothing seen through X11 tells a tiling desk apart, so the library goes by the name of the desk.
On X11 the toolkit guesses the insets of a window with the desk border before it is mapped and corrects them after, so the window can come out taller than its picture, by up to the height of the title bar.
COSMIC draws the desk border outside the X11 window and sets no _NET_FRAME_EXTENTS: the toolkit keeps its guess of the insets, and keeps a position of the window that COSMIC has changed without telling it.
On COSMIC the library takes the position and the size of a window from the X server (XGetGeometry, XTranslateCoordinates), and sets a size with XResizeWindow on the X11 window, the content area, so that the toolkit learns the new size from the configure event that follows.
The drags handed to COSMIC are _NET_WM_MOVERESIZE messages sent after releasing the pointer grab of the toolkit's own X11 connection; the release comes back to the window because the pointer is over the Fearless corner when the desk's move or resize ends.
A desk move from state 1 would start with the pointer away from the window, since COSMIC leaves full screen at a position it remembers; a desk move that ends with the pointer away from the window sends no release to it.
COSMIC gives a new window the size it remembers for the program, and a window leaving full screen its own size after the library has set one: the library sets its size again once COSMIC manages the window (WM_STATE) and the window is out of the full screen state and off the bounds of the screen.
COSMIC reports a window unmaximized before giving it the restore size: on COSMIC the library decides on an unmaximize once the window has the size of the restore size, and a window at the restore size and position is a transition to 1.
On Windows the library sets the restore size itself (SetWindowPlacement), and a window at exactly the restore size is a transition to 1.
On X11 the library takes both the maximized state and the geometry from the X server (_NET_WM_STATE, XGetGeometry), in the order the desk sets them: the state changes first, the geometry follows.
The toolkit is no source for this decision: it reports the state change after the X server has the new geometry, and under KDE Plasma it keeps the bounds of a maximized window at the restore bounds, with guessed borders.
GNOME maximizes a window that maps wider than 80% of the width and taller than 80% of the height of the work area, and gives that maximized state back when the window leaves full screen.
Off Windows, the library maps a window entering state 1 at the leaving bounds of state 1 before asking for full screen.
Leaving full screen, Cinnamon can give the window its size from before full screen after the library has set the new one: a corner drag takes the size of the window from the bounds the library set last, not from the toolkit.
KDE Plasma marks a window without the desk border that covers the height of the work area as maximized (_NET_WM_STATE_MAXIMIZED_VERT and _HORZ), and keeps the mark after the window shrinks: the maximized state of the toolkit means state 3 only for a window with the desk border.
KDE Plasma on Wayland honours the position the library sets, publishes _NET_WORKAREA and _NET_FRAME_EXTENTS, and shows the icon of the window in its taskbar.
GNOME and COSMIC show in the dock and in the window picker the name and the icon of the .desktop file whose StartupWMClass is the WM_CLASS of the window, and the WM_CLASS with a generic icon when there is none; they do not show the icon of the window.
The window class of a main and an icon is <identity>-<hash of the project folder and the main>-<icon>, with <identity> the identity of the manager in its file associations.
The manager installs, as part of its file associations, one hidden .desktop file (NoDisplay=true) for each icon each main preloads, with that icon and that window class as StartupWMClass: the reconcile that writes, replaces and removes the file associations does the same with these files.
The manager passes the child JVM of a main the window class without the icon (-DfearlessDesk.id), the folder of the installed icons (-DfearlessDesk.icons) and the command that opens the project in the manager (-DfearlessDesk.relaunch).
The toolkit sets WM_CLASS from the class of the bottom frame of the thread that starts it, the main class, when it creates each window: the library sets XToolkit.awtAppClassName to the window class of the icon before each window is created; the runtime opens java.desktop/sun.awt.X11 to the library.
The Windows taskbar groups windows by their AppUserModelID, and without one by their program file: every Fearless program runs on the same java.exe.
On Windows the library gives each window the window class as its AppUserModelID, with the .ico file of the icon as RelaunchIconResource, and the name of the Gui and the relaunch command as RelaunchDisplayNameResource and RelaunchCommand: the taskbar ignores RelaunchIconResource without the other two.
These are properties of the property store of the window (SHGetPropertyStoreForWindow), set after the toolkit creates the native window and before it is shown.
Without the manager the library leaves WM_CLASS and the AppUserModelID as the toolkit sets them.

A size the library sets comes back from the toolkit up to one pixel different on a desk scaled above 100%: a content area within one pixel of the size the library chose is the library's, and sends no ResizeRequest.
The pointer buttons are read from the platform on each repaint tick, through the Java foreign function API (the runtime enables native access for the library module): GetAsyncKeyState of the left, right and middle buttons on Windows, the button mask of XQueryPointer on the root window on X11, CGEventSourceButtonState on macOS.
The desk's minimum size is setMinimumSize: the smallest window whose content area holds the rectangle with the aspect ratio of the virtual pixel space that covers minArea, desk border included.
The Windows peer of the toolkit hands the desk the minimum size in user space while the desk reads it in device pixels; on Windows the frame reports the minimum multiplied by the display scale to the peer, and the plain minimum inside Window.reshape, which checks in user space every size given to the window, the growth by setMinimumSize included.
Windows restores a maximized window to at least the desk's minimum size, and a ResizeRequest accepted in state 3 can raise the minimum size above the restore size: on Windows the library grows the restore size to the minimum size each time it sets the minimum size of a maximized window, so that the unmaximize still gives exactly the restore size.

The opacity goes through setOpacity, which the toolkit allows only on an undecorated window that is not the full screen window.
On macOS, Cmd+Q ends the process without a windowClosing unless the quit strategy is CLOSE_ALL_WINDOWS; the runtime sets it, so Cmd+Q is a close request.
