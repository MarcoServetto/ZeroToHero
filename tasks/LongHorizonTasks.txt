Add a compile-time check in the Fearless Coordinator: when a package is compiled, for every method whose Fearless source has a real body (not abstract `;`, not a literal `Magic!` body), assert that no hand-written class under StandardLibrary's rt/ folder (and sub folders) both implements that method's generated interface AND overrides that method's mangled name. If one does, fail the build — two independent implementations of the same method must never coexist silently, since only the native one ever runs and nothing today checks they agree.

Motivation: FearlessLang/StandardLibrary PR #45 (still open) fixes Int.wrapIndex in int.fear, whose guard was inverted (`len == 0` instead of `len != 0`). This was invisible because StandardLibrary/rt/Int$c$0Instance.java has a hand-written imm$wrapIndex$1 override that was correct and is the only implementation that ever actually runs (Int$c$0Instance is the only concrete class ever instantiated for Int) — the buggy Fearless body compiled fine and was never exercised.

Where things live:
- Coordinator/src/naiveBackend/Backend.java: generateInterface/emitTopMethod (~line 119-131) is where every bodied Fearless method becomes a Java `default` method on the type's generated interface. mangledMethodName(rc,m) (line 158) produces the name a native override must match (e.g. imm$wrapIndex$1); decTypeName(n) (line 146) produces the generated interface name (e.g. Int$c$0).
- Coordinator/src/naiveBackend/NaiveBackendLogicMain.java (line 19-25) already receives rtPath and copies StandardLibrary/rt/*.java into every compiled package's output — the source folder to scan is already threaded through this call chain.
- StandardLibrary/rt/*.java: study Int$c$0Instance.java as the running example.
- Abstract-ness is `m.impl().isEmpty()` (Frontend/FearlessFrontend/src/inject/Methods.java:264) — already excluded by Backend's existing abs() branch, no new work needed there. Separately, `Magic!` (used in base/var.fear, base/caching.fear, base/errors.fear, base/_rank_base000.fear — not in the numeric types) is a body that IS present syntactically but means "native only, no real Fearless semantics" — trace how to detect a literal Magic! body from core.E at the point Backend.java sees it, and exclude it too.
- Match by INTERFACE (a native class's `implements` clause, matched via decTypeName), never by bare method name — Byte, Int, and Nat all separately declare a bodied `.rem`, but only Byte$o$0Instance.java overrides imm$rem$1; matching by name alone wrongly flags Int.rem and Nat.rem too.

Do not add a unit test checking this triggers only when needed, it would have to basically rebuild base and it would be quite slow, just experiment to see if it catches a newly introduced similar bug and record the success.

Run the full TestAllFrontendCoordinatorIntegration.java before opening the PR, since this touches codegen used everywhere.

Task:
We are expanding the state and correspondingly the gui of the fearless manager.
Before, a loaded project currently can be in states:
-invalid content (file names etc)
-not compiled no cache (no .fearless_out folder)
-not compiled .fearless_out out of date
-compiled
-compiled and running

Now we are moving to the following:

-data:invalid content (file names etc)
-code:invalid content (file names etc)
-data:valid idle project
-data:read write
-data:read only 
-code:not compiled no cache (no .fearless_out folder)
-code:not compiled .fearless_out out of date
-code:compiled
-code:compiled and running

The manager need to show the current state and the user need to be able to move between states using the gui when reasonable; the state of each folder should be saved in the manager data.
Moving in and out of invalid content: not done via the manager, done by changing the content on the hard drive, the manager discovers the change and moves the project in or out of invalid content.
On default a folder with valid content that has not being acted upon in any way should start as data:valid idle project.
a data:valid idle project should show buttons to become 'some kind of project'.
-Become data->
It becomes a data:read only project; similar to the mains to select, we now have to select what 'code' projects can read it; and near each one we can override a default and write a list of aliases, with the first element prewritten to be the standard filename to type conversion.

-Become editable data->
It becomes a data:read write project; similar to the mains to select, we now have to select what 'code' projects can read it; and near each one we can tick a box to allow writing, and override a default and write a list of aliases with the first element prewritten to be the standard filename to type conversion.

-Become code->
It becomes code:not compiled no cache; this is the starting point for the current manager. we will see the compile button that can be replaced by the run button with main selection etc exactly as today.
The project will then 'naturally' move between the code kinds depending on the pressed buttons.
The code will now also have a list of 'reads' and 'edits' with maps from project names to aliases as for before. Crucially those are just two views over the same data, not separated lists of permissions that have to agree.

all the Data and Code kinds will have a button to go back to data:valid idle project (except data:valid idle project otherwise it would be a no op)

Each kind will now have a different badge; currently we have a few badges including ! and X. Those are pretty good! we just need more kinds.

As you can imagine, later on we will have APIs to allow code projects to read/edit data in Data projects.
