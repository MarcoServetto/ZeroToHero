"a data parallel region starts only after the stages before it have finished":
Read the sections "++ is a fence, and sends read or imm elements downstream", "Duplicated `mut` elements", "Modes: the type of the source enables parallelism" and "Sources and modes".
The document is now confusing.
- "Sources and modes" says `Seq` allows only the sequential strategy.
- "++ is a fence..." says the stages after a `++` can run data parallel even in mode `Seq`, and that "it is the fence, not the types alone, that makes this sound".
Clarify that this only happens to a flow with no hintSequential.

Task: Tour/StandardLibrary better object capability explanation and framing
It is now clear that actually you need an object capability to OBSERVE side effects, not to perform them.
The whole point is to ensure deterministic/unobservable parallelism/caching/computation/invariants etc.
So by restricting what sources of input code can get, we ensure more predictable behaviour.
On the other side, Debug can always just 'perform' side effects, non termination can be performed all the time just never observed,
etc etc. Look at Logs, that can be performed any time but only read with the permission.
Can you draft some better text in the tour to focus on this perspective and see if anything in the standard library need to change?
The dressing of 'doing something' requires an object that can do that something makes perfect sense, the point is that an object that 'does' something unobservable is kind of transparent?
Make a Pr with the results.
