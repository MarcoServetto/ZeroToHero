This task is a single tasks with many rounds.
Do not start a sub agent for this task, the task itself asks you to start sub agents for the inner tasks.
Since win1,2,coordinator will be idle, at any given moment in time, there should be two agents active: you (outer) and the inner agent.

Task "FrontendBugs":
You (win3) are the outer agent; the sub agents you start are the inner agents.
Run at most one inner agent at a time. Every agent should be Opus 5.5 high.
Inner agents write no logs; this task overrides the global rule on sub agent logs.
Every inner agent starts in a fresh environment, with no trace of the activity of earlier inner agents.

Setup:
- If a PR of this task from an earlier night is still open on
  FearlessLang/Frontend, stop and report it.
- Otherwise, in your working copy of Frontend, create the branch
  FrontendBugs from upstream main, push an empty commit, and open the PR.
- Run TestAllFrontend.java and note the failing tests.

Rounds:
Before each step, check the usage limits. Do not worry about getting near the weekly limit, all good.
If the current 5 hours session is over 80%, sleep until 5 minutes after the session resets,
as the overnight rules describe.
Do not start a new round after 8am.
1. Copy FearlessFrontend/src of the branch into a new empty folder <folder> in your
   scratchpad, without any git data, together with
   ZeroToHero/tasks/ruledOut/FrontendBugs (as <folder>/ruledOut) and, when it exists,
   C:\data\fearlessPaper\Fearless_TOPLAS without its git data (as <folder>/paper).
   Start an inner agent:
   """Read only files inside <folder>. Read all the code in <folder>/src.
   <folder>/paper, when present, is a paper whose type system describes the same
   language as <folder>/src/typeSystem.
   Identify one bug or inconsistent behaviour in the code.
   Think about the logic of the code.
   Then write a test showing that the bug is real. Do not fix the bug.
   The behaviour marked Good in <folder>/ruledOut is intended.
   Reply with the kind of bug and one concrete Fearless
   program with the wrong result it produces: a wrong error, a missing error, or a crash. Do not run your tests showing that the bug is real,
   focus on reasoning only. Running the tests is not your responsibility."""
2. Delete the folder. Run the test(s) yourself and decide if the bug is real.
   Record it in ZeroToHero/tasks/ideas/FrontendBugs: one line per kind of bug,
   marked reported or refused, with how many times it was proposed; a kind already in the file, even with different words, increases its count.
   If you refuse it, go back to 1. After 5 refusals in a row, stop.
3. 
   Open a new PR for this specific bug on frontend.
   Start an inner agent:
   """On the branch FrontendBugs of Frontend, read all the code in
   FearlessFrontend/src and consider this bug report <provide bug report PR link>.
   Run TestAllFrontend.java: only these tests and the new ones may fail: <list>.
   Is this bug an isolated thing or can it be generalised in a category of wrong behaviour? Fix either the isolated bug or the whole category of behaviour.
   Check that the bug is now fixed by seeing the tests pass. If the bug was not an isolated case, add more tests to cover other representative cases.
   Do not add redundant tests.
   Amend the PR."""
4. Read the new state of the PR. Decide if any twists is needed. Make sure to record the bug in TypeSystemBugs.md.

Stop when one the following is true:
- there are at least 10 different PRs for 10 different bugs
- the refusal limit is reached (this may be because the same bug is encountered over and over again)
- some of the encountered bug is preventing the agents to find new bugs because the found bugs interact badly with finding new ones until those PRs are integrated.
- the time limit is reached.

Otherwise, restart from point 1, while providing the agents with the code of Frontend as it is now, not as it would be with those PRs accepted.

Make sure at the end there is a PR for Frontend, and one for ZeroToHero with the
ideas file and the done tasks.
