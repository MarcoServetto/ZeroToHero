Long Task:
We want to design a new API for running a lambda on a new thread with different stack space;
need to also allow for optionally running on the same thread if enough stack space is present; or if we have called that recursively not too many times on the same thread.
example deeply recursive algorithm can use it on every rec step and need to be fast enough.

In Java it is semi common to make a new thread start it and wait for it just to get an injection of useful stack space, for example to run a deep recursive deserialization.
Fearless lambda based mindset should make this easy:

RunRecursion#{..}
should run the lambda in a new Thread with 'large' heap.
We may want more options to tune this, but we need to examine very clearly what happens on real vms, it is not the case that passing a specific stack parameter gives you exactly that stack amount. What is that we can 'trust' or semi trust it would work?

`RunRecursion:{#[R:**](mut MF[R]):R->Magic!}`
is the general idea. If a run recursion is called in another run recursion (stack trace can be inspected, but there may be better ways, like checking thread local stuff) we may just run the lambda. Some parameter or some tuning could help, we could have families and layers.
For example
Parsing:RunRecursion{.dept->7}//thus overriding some default constants
Sorting:RunRecursion{.dept->34}
and now if Parsing calls Sorting, different family new thread.
But if Parsing calls Parsing we just grow a counter until we get to 7 nested calls then we go new thread.
(the counter will just use a try finally to go down around the lambda execution)

Does this design make sense?
What are other people doing around this kind of design?
What other overridable constants we may want?
Implement it and open a PR, add some tests using this set up and see if it make sense in some practical cases.
