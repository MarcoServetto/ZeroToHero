Fearless contributor setup

Goal

A student or a cooperator downloads one archive, extracts it and starts one program: the setup program.
The setup program fills one folder, the setup folder, chosen by the student.
The setup folder has four sub folders:
  jdk        the pinned JDK
  eclipse    the pinned Eclipse IDE for Java Developers
  workspace  the Eclipse workspace
  repos      the checkouts of the Fearless repositories (choice 1 and choice 3 below)
When Eclipse opens on that workspace, everything is already set up.
Every Eclipse project compiles with zero errors.
The JUnit tests and the Java scripts of Coordinator/Build/src/scripts run from the Eclipse Run menu.
Deleting the setup folder is the reset to zero.
Running the setup program again on a complete setup folder opens Eclipse on it.
Running the setup program again on an incomplete setup folder completes it.

Distribution

The setup program is distributed as the demo of https://github.com/marcoautomation2/fearless_gui_demo is distributed.
The repository is marcoautomation2/fearless_setup.
Its build/Build.java and its GitHub Actions workflow build a jpackage app image for Linux (tar.gz) and for Windows (zip).
The app image contains its own Java runtime: the student needs no Java to start the setup program.
A push to main publishes the two archives in the release `setup`.
A push to any other branch publishes the two archives in the prerelease `test`.
The README tells the student what to download, how to extract it and how to start it, including the warning an unsigned program gets on Windows.

Pinned versions

One place at the start of one source file holds every download: URL and SHA-256 of
the JDK (Temurin 26.0.2) for Linux x64 and Windows x64,
the Eclipse IDE for Java Developers 2026-06 for Linux x64 and Windows x64,
the flexmark jars listed in FearlessTour/externalJars/readme.txt.
Moving to a new JDK or a new Eclipse changes only that place.
Every download is checked against its SHA-256.
Every archive is extracted into a temporary sibling folder and renamed into place only when complete, so an interrupted run leaves no half folder that looks complete.
Linux archives are tar.gz: the setup program extracts them itself, restoring executable permissions and symbolic links.

The repositories

The setup program covers Commons, Frontend, Coordinator (including Coordinator/Build), StandardLibrary, FearlessTour and ZeroToHero.
Controllers is checked out too, so that the Java scripts build it, but Controllers gets no Eclipse project.
The repositories stay IDE agnostic: nothing is added to them for this setup program.
Everything Eclipse needs (.project, .classpath, .settings, launch configurations, output folders) lives in the workspace folder.
The Eclipse projects live in the workspace folder and link to the source folders in the checkouts.
After setup, and after Eclipse has built everything, `git status` is clean in every checkout.
The setup program writes the gitignored files the build needs:
Coordinator/Build/src/resources/LocalResources.java, pointing at the checkouts and at the eclipse folder of the setup folder,
and the flexmark jars in FearlessTour/externalJars.
Anything else the build needs that a fresh clone lacks is found by the tests below and added to the setup program.

The three choices

Choice 1, official checkout:
the setup program clones the seven official repositories with JGit into repos, without any login.
The student can build, run and change the code, but cannot push.
The setup program says so before the student picks choice 1.

Choice 2, existing folder:
the student points at a folder holding the seven checkouts, official or forks.
The setup program checks that each of the seven checkouts is there and looks right.
When something is missing, the setup program names the exact folder and what is missing in it.
The setup program never changes a tracked file of those checkouts.

Choice 3, forks:
the setup program guides the student, step by step, to fork the seven repositories on GitHub, with one link per fork page.
The setup program guides the student to install GitHub Desktop on Windows, or git on Linux, and to sign in there.
The setup program guides the student to clone each fork into its folder under repos.
The setup program does not clone anything and does not touch git: GitHub Desktop or git do the clone and keep the credentials.
The setup program never asks for a password or a token.
When the student says the clones are done, the setup program checks repos as in choice 2, and goes to the next step only when the files look right.

Java inside Eclipse

Eclipse runs on the JDK of the setup folder (`-vm` in eclipse.ini).
The Installed JREs of the workspace list exactly one JDK: the JDK of the setup folder.
Eclipse never detects or adds other JDKs, including a JDK on the PATH or in JAVA_HOME.
The default VM arguments of that JDK include `-ea`, so every launch runs with assertions on.
The workspace uses UTF-8 and LF line endings for new files.
The first start of Eclipse shows the workbench with every project already there: no workspace dialog, no welcome page, no import, no question.

How to configure Eclipse

Two ways are acceptable:
writing the workspace .metadata files directly, after setting up one workspace by hand through the Eclipse GUI and reading what Eclipse wrote,
or driving Oomph (part of the Eclipse IDE for Java Developers) without its GUI.
The agents pick the way that gives the smaller code passing every test below, and say why in the PR.

Fool proof

The tests below include at least:
a setup folder path with spaces and with a non ASCII letter;
a setup folder deep enough that Windows paths get long;
another JDK on the PATH and in JAVA_HOME;
another Eclipse already installed;
the setup program killed during a download, during an extraction and during a clone, then started again;
no network, then network again;
a choice 2 folder with one checkout missing, and with one checkout of the wrong repository;
a choice 3 repos folder with one fork cloned into the wrong folder.
In every case the setup program either completes, or stops with a message that tells the student exactly what to do.

Code

The code follows the coding rules of the agents (offensive programming, minimality, style).
The code is as small as possible.
The error messages follow the style of Frontend.

Test on a desk

A test acts as a person acts and checks what a person sees (the GUI rules of the agents and the gym files).
A test starts from the archive the GitHub workflow published, never from a local build.
A test downloads, extracts and starts the setup program, picks a choice, opens Eclipse, and then checks:
the Problems view shows no error;
TestAllFrontend runs from the Run menu and passes;
one JUnit test of Frontend runs from Eclipse and passes;
a launch has assertions on;
an edit of a Java file in Eclipse compiles;
`git status` is clean in every checkout;
the steps are something a first year student does without help.
Linux tests run in the VMs (/data/gym/gui_vms_gym.txt): every `vm.sh open` starts the VM from its clean disk.
The archive reaches a VM through /data/pilotio.
Each Linux turn tests at least three different VMs, and over the night every VM is tested at least once.
Windows tests run in the cleanest environment the Windows machine offers: Windows Sandbox when it is available, else a new local user account, else a folder outside C:\data with PATH and JAVA_HOME pointing at another JDK.
The Windows report names the environment used.

The coordination protocol

linux3 and win3 work on the same pull request of marcoautomation2/fearless_setup: the PR.
They talk only through the PR.
Every turn ends with a push to the branch of the PR and a PR comment.
The first line of that comment is exactly `turn: windows`, `turn: linux` or `done`.
The rest of that comment says what was tested (desks, environments, choices), what failed, what changed, and what the other side tests next.
The latest PR comment whose first line is one of those three lines says whose turn it is.
A side waits with a 30 minute timer: a background sleep command, whose end wakes the agent.
On each wake the waiting side reads the PR comments; when the turn is its own, it starts its turn, else it sets another 30 minute timer.

linux3 starts.
linux3 creates marcoautomation2/fearless_setup, writes the first complete version, tests it on Linux, opens the PR (base main, head a branch of the same repository), and comments `turn: windows`.
The PR description tells win3 how to take it from there.
win3 sets a 3 hour timer when its night starts, then waits with 30 minute timers.

Each turn:
test the PR on the desks of the own machine;
fix what the tests find;
send a fresh Opus 5.5 high sub agent to read the full code, ignoring the git history and the earlier turns, and to simplify, minimise, grow consistency and find bugs, with the tests above as evidence;
test again on the desks of the own machine;
push and comment, handing the turn to the other side.

No turn starts after 06:00.
The side holding the turn at 06:00 finishes its turn by 07:00, tests the final state on its own machine, and comments `done` with a summary: what works, what is still fragile, what the user tests first.
A side that reads `done`, or reaches 07:00 while waiting, stops.
Nobody merges the PR: the user reviews it.
