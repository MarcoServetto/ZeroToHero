= Distractions =
Every caveat, every clarification about something met later and every parenthetical pulls the reader away from the point of the paragraph. Never add them.

Good:
  From the point of view of Fearless newlines and spaces are irrelevant; any amount of spacing is equally effective at separating pieces of code
Bad:
  From the point of view of Fearless newlines and spaces between tokens are irrelevant (text in quotes, which we meet later, is the exception); any amount of spacing is equally effective at separating pieces of code
Explanation: the reader is learning what a token is; strings are met later and are a distraction here.

Good:
  This method uses the Pythagorean theorem, but it is not ideal:
    - we duplicate code for `p1.x - (p2.x)` and `p1.y - (p2.y)`
    - all the code is in a single hard to read line.
Bad:
  This method uses the Pythagorean theorem, but it is not ideal:
    - we duplicate code for `p1.x - (p2.x)` and `p1.y - (p2.y)`
    - all the code is in a single hard to read line.
    - with `Nat` coordinates, `p1.x - (p2.x)` stops the execution when `p2.x` is bigger than `p1.x`, since a `Nat` can not be negative (the underflow we discussed before). We ignore this problem here.
Explanation: mentioning a problem in order to say it is ignored is not ignoring it. The section is about local names, and the underflow is the same with or without them: a problem unrelated to the point of the section is a distraction.

Good:
  Fearless offers good ways to handle this other case, but we will see them later in the guide.
Bad:
  Fearless offers good ways to handle this other case, but we will see them later in the guide (the section about offensive programming, in Chapter 4).
Explanation: a pointer to a far chapter is a distraction; "later in the guide" is enough.

= Over explaining =
A sentence that is clear to the reader stays as it is, even when a more precise or more complete version exists. Dropping a word that carries no meaning is fine; replacing it with an explanation is not.

Good:
  - `.turn -> East;` is a **method declaration** and in this case
Bad:
  - `.turn -> East;` is a **method implementation** (a method declaration with a body) and in this case
Explanation: the distinction does not matter at this point, and the parenthetical is a definition nobody asked for.

Good:
  We will use the term 'object' to talk about those.
Bad:
  We will mostly use the term 'object' to talk about those; the terminology recap at the end of this chapter explains when the other names are used.
Explanation: "consistently" in the original carries no meaning and can go; the rest of the Bad version explains a choice the reader has no reason to question.

Good:
  Method `Rotation+` has two parameters: `this` and `r`; the two `Rotation`s we want to compose.
Bad:
  Method `Rotation+` has two parameters, counting `this`: `this` and `r`; the two `Rotation`s we want to compose.

Good:
  In order to obtain `7`, those parentheses are needed.
Bad:
  In order to obtain `7` from `1 + 2 * 3`, the parentheses around `2 * 3` are needed.
Explanation: the reduction right above makes the sentence clear; repeating its content only makes it longer.

= Text without a reason the reader can see =
Every added sentence answers a question the reader has at that point. A term appearing somewhere else, or the existence of a textbook name for a concept, is not such a reason.

Good:
  This process of discovering the meaning of an expression is called evaluation.
Bad:
  This process of discovering the meaning of an expression is called evaluation; each step, replacing a call with what it returns, is called a reduction.
Explanation: the reduction table below shows what reducing means by example.

Good:
  The crucial consideration is that we already have a name for the concept of a function that takes a direction and rotates it: `Rotation`.
  ...
  The object literal `{ d -> this#( r#(d) ) }` creates a new `Rotation` object. When this new object's `#` method is called later, it will use the `this` and `r` that were captured when it was created.
Bad:
  ... it will use the `this` and `r` that were captured when it was created.
  In other words, `Turn90+(Turn180)` is `RotateTwice` with its first two parameters already given: a `Rotation` that still waits for a `Direction`.
  Giving a function only some of its arguments, to obtain a function that waits for the others, is called **partial application**.
Explanation: partial application is introduced by the question that opens the section; naming it again is repetition.

= Hedges =
A statement true for everything the reader knows is stated as true. "So far", "usually", "mostly", "among others" make the reader wonder about cases the guide has not shown.

Good:
  In other words, there are exactly two ways to refer to an object:
Bad:
  In other words, so far there are two ways to refer to an object:
Explanation: the reader asks which other ways there are, and the guide never shows them.

= Terms are chosen for how the reader understands them =
The guide juggles terms for the meaning the reader already gives them, not for what they mean in the technical vocabulary. Replacing a word with the technically correct one breaks the reader's understanding.

Good:
  `TODO:` is a short 5 symbol annotation meaning that there is an open task.
Bad:
  `TODO:` is a short 5 character annotation meaning that there is an open task.
Explanation: many people do not think of `;` or `:` as a character; "symbol" is how they understand it.

Good:
  If we ignore parentheses in strings and comments, a Fearless program always has balanced parentheses.
Bad:
  If we ignore brackets in strings and comments, a Fearless program always has balanced brackets.

Good:
  Here we see the generic type `[Val]`.
  >`Fork` has a generic method `.choose` that forall types `Val` takes two arguments of type `Val` and returns a `Val`.
Bad:
  Here we see the generic type parameter `Val`, declared by `[Val]`.
  >`Fork` has a generic method `.choose` that forall types `Val` takes two parameters of type `Val` and returns a `Val`.

= Inference =

Good:
  Here, if we were to omit `WidenTo[Direction]`, the code
  ...
  may fail to compile:
  the inference would see `.north -> East;` and may conclude that the method `.north` is returning `East` of type `East`, thus this match should return an `East` instead of a direction.
Good:
  `Foo#(bar)` may not compile: you may have to write `Foo#[Bar](bar)`, or help the inference in other ways.
Bad:
  Here, if we were to omit `WidenTo[Direction]`, the `.turn` above would still compile, since it declares its return type `Direction`.
  However, the code
  ...
  would fail to compile:
  the inference would see `.north -> East;` and conclude that the method `.north` is returning `East` of type `East`, thus this match should return an `East` instead of a direction.
Explanation: the inference is intentionally in a state of flux, so that it can be improved later. The guide talks about what the inference does in terms of "may": code that may not compile, and the ways to help the inference. A "may" sentence stays true when the current inference happens to accept the code; the guide never describes exactly what the current inference accepts or rejects.

= Source conventions =

Good:
  +-*|/=<>,.;:()[]{}`'"!?@#$%^&_|~\
Bad:
  +-*/=<>,.;:()[]{}`'"!?@#$%^&_|~\
Explanation: "*/" would end the Java comment; "*|/" is rewritten as "*/" during the html generation.
