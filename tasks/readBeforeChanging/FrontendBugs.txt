Good:
  Inference produces only code that is accepted when written by hand.
  A:{ read .b: mutH B -> {} }   infers   A:{ read .b: mutH B -> mut B }
Bad:
  A:{ read .b: mutH B -> {} }   infers   A:{ read .b: mutH B -> mutH B }
Why: the parser rejects mutH and readH in front of an object literal.

Good:
  The programmer has three expressions: object literal, parameter, method call.
  A, A{}, mut A{}, 43 and {} are object literals without methods.
  The full frontend turns each of them into a type expression as soon as its head is known, with no declaration and no fresh name; the compact frontend keeps them as literals and is the oracle: a disagreement is a bug of the full frontend.
  A{'self}   is rejected: self name "self" is dead code
  base.Void   is accepted in every package; Foo:base.Void{} and Foo:43{} are rejected: an anonymous object literal without methods declares nothing, a declaration implements
  l.fold(Zero, f)   infers the type argument from f too; l.fold(Z:Zero{}, f) fixes it to Z
  An error message says "object literal", "parameter" or "method call"; a type expression is an "object literal instance of" its type.
Bad:
  An error message says "type expression".
Why: every rule about an anonymous object literal without methods (sealed, WidenTo, type argument inference) is a rule about the literal; the type expression is only an optimization of the full frontend.

Good:
  base.BaseContainer and base.Sealed are only implemented; code using them as a type may be rejected.

Good:
  An override refines only nominal types: X and rc X are the same when the bound of X is exactly {rc}.
  Sup:{ mut .h: mut P }  Sub:Sup{ mut .h: iso P }   is rejected

Good:
  Foo[T:*]:{}  A:Foo[imm Bar],Foo[mut Beer]{}   is accepted
  Foo[T:*]:{ .get: T }  A:Foo[imm Bar],Foo[mut Beer]{}   is rejected
Why: overriding decides whether the methods of the two supertypes can be reconciled.

Good:
  The self name of a base.CaptureFree declaration, at top level or inside a method, has the capability of the declaration (imm by default) in every method, also when the declaration is created as mut.
  A:base.CaptureFree{ read .me: imm A -> this }   is accepted
Why: an instance of a CaptureFree type has an empty ROG, so a mut and an imm reference to it observe the same.

Good:
  A literal capturing only iso and imm values, with no abstract mut method, is born iso whatever capability is written in front of it; its self name has the written capability (imm by default).
  Make:{ #: iso A -> imm A{'self read .me: imm A -> self } }   is accepted

Good:
  Values imm in practice but not typed imm are not tracked; sound programs relying on them may be rejected, also where a similar case is accepted. Programs call the standard library methods that turn such values into imm.
  A:{ read .me: imm A -> this }   is rejected

Good:
  A generic method is checked once, under the bounds of its type variables: with a bound of several capabilities a program may be rejected even if each single capability gives an accepted program. The paper agrees.
  Clone[E]:{ read #(e: read E): mut E }  U:{ .dup[E:*](c: Clone[imm E], e: E): E -> c#e }   is rejected
  A:{ .m[Z:imm,readH](a: read/imm Z): Z -> a }   is rejected
  Box[T:**]:{}  Sub:{ .m[X:mut,read](x: Box[read X]): Box[read/imm X] -> x }   is rejected, type arguments are compared as written
  Get[Y:*]:{ mut .get: Y }  A:{ .m[X:iso,mut](x: X): mut Get[read/imm X] -> mut Get[read/imm X]{ mut .get: read/imm X -> x } }   is rejected, x is seen as read X in a mut method
Why: checking each capability separately costs performance and complicates the formalism.

Good:
  An iso captured by a literal is imm inside the literal; Block#.openIso gives a literal a mut view.
  A:{ .mk(x: iso S): mut H -> mut H{ .get -> x } }   is rejected
Bad:
  A:{ .mk(x: iso S): mut H -> mut H{ .get -> x } }   is accepted, x captured as mut
Why: choosing mut by the shape of the code rejects literals that need imm; choosing by need makes capture depend on inference.

Good:
  A:{ Block#.let _ = {5} .return {2} }   is rejected
Why: the .let desugaring is not worth it for an unused value.

Good:
  A:{ .m(x: A): A; .m(x: A, y: A): A }
  B:A{ .m -> :: }   is accepted, as .m(x) -> x
  B:A{ .m(x) -> ::.foo(x) }   is rejected
Bad:
  B:A{ .m(x) -> ::.foo(x) }   is accepted, as .m(x, y) -> y.foo(x)

Good:
  A very deep input (a huge comment or string, deep nesting, a long call chain) may end in a StackOverflowError; catching it and reporting a good error is the only improvement wanted.
Why: recursion is the natural shape of parser, inference and type system.

Good:
  A read or imm literal without a self name may implement a mut method; no dead code error.
Why: the literal is promoted to iso before its methods are checked.

Good:
  A:{ mut .foo: A }  Need#(A{})   gives no hint to write mut A{}; read A{} gets that hint.
Why: a literal without capability is imm by default, and mut A{} would also need .foo.
