Three Flow Designs

The Legacy push design rebuilt in the runtime as Legacy+, the speculative design of PR 70 as fearless70, and the JDK-stream runtime on main: what each guarantees, where each lets non-determinism through, what they cost, and what one taught the other.

Scope and the three runtimes

All three implement the same flow.fear API (fearless70 and Legacy+ also make the six methods that were Error.msg TODO work). A parallel flow is read/imm List.flow, List.flow(mode), EList.flow(mode) and ESet.flow; everything else (Flows#, seqFlow, ranges, Map, Opt) is sequential in all three.

main

  • Flow$o$1Instance wraps a JDK stream; parallel sources call stream().parallel().
  • Consumers that pull through an iterator (first, get, fold, last) run sequentially; list, forEach, eSet, mapping, any run on the fork-join pool.
  • Order is lost where a LinkedHashMap is filled from several threads; the error reported is the first in time; nothing is cancelled.

fearless70 (PR 88, from PR 70)

  • Stateless stages (map, filter, flatMap) are recorded as a chain of consumers; a terminal cuts the list into chunks that double from 1 to n/(4p), common-pool tasks, each publishing every output as it exists.
  • The consumer is a sequential JDK stream over the chunks in encounter order, so every stateful op and terminal is the plain JDK one.
  • Closing the stream cancels: queued chunks never start, running ones stop at their next element or Yield#.

Legacy+ (PR 87)

  • Push model: FlowOp.step/forAll(sink), Sink#/pushError/stopDown; every stage is a Java class of FlowOps.java (Legacy wrote them in Fearless over magic primitives).
  • Data parallel: the list source splits in halves into up to 2*cpus tasks on virtual threads under a budget of 4*cpus permits (past it, a task runs inline and its nested flows sequentially); each task fills a buffer; one flusher drains the buffers in task order into the terminal.
  • A stateful stage after a data-parallel source turns the rest into a pipeline: the parallel part feeds a queue, every later stage runs on a thread of its own with a 512-slot queue.

Legacy+ is "the current Fearless with only the flow inner workings imported from LegacyFearless": the EOD strategy and the pipeline machinery that Legacy actually ran, in rt/FlowOps.java, rt/DataParallel.java, rt/PipelineParallel.java and rt/Flows$1c$0.java, with the FlowCreator promotion rules (sequentialised or one element: sequential; three: pipeline; else data parallel). What Legacy did not have and the current API needs (++, set, eSet, mapping, eList, a counting size) is added; what Legacy had and lost in its virtual thread (a non-deterministic error inside the parallel part of a converted flow) now reaches the consumer.

Where non-determinism gets through

The promise under test: a parallel flow is observationally the sequential flow of the same source. Ten checks in testFlowDeterminism, a diverging-element program in testFlowTermination (PR 86 and Coordinator PR 159), and the cancellation checks in each runtime's test_flow_parallel.fear.

Legacy+ allowed, fearless70 prevented

Termination. Every Legacy terminal waits for every task, so a lambda that diverges past the decision hangs first!, any, limit. Porting Yield# (a thread-local "source of the current task", checked at every element and every Yield#) fixes the cooperative case; the uncooperative one stays, and cannot be fixed without abandoning the join.

Two bugs found by porting Yield, both Legacy's threading model. With Yield# in place the boom5-then-looping test still hung: a deterministic error reaching the terminal did not stop the flow (fearless70 cancels on close of the stream), and once fixed, the 15 spinning tasks pinned all 8 carriers so the flusher, a virtual thread, never ran to deliver the error. Virtual threads are never preempted while computing: the flusher is now a platform thread and Yield# also hands its carrier over. The same hazard remains for pipeline stages, which are virtual threads doing the stage work.

Order of a later non-deterministic error. Legacy+ reports a later task's non-deterministic failure over an earlier deterministic one (the task records it before the flusher meets the deterministic message). Non-deterministic errors need no order: they are observable only through a capability, so the tests do not require it.

fearless70 allowed, Legacy+ prevented

A mutation observed in progress. For flows of mut elements (ParRepr, ParPod) the caller still owns the elements. fearless70 returned from first! while workers were inside r.mutate{...} on other elements; the check that followed read a Repr between the two increments of one mutation. Legacy+ never exhibits this because every terminal joins. PR 88 now joins the running chunks when the flow's elements are mutable, and keeps returning at once for read/imm elements.

A mutation cut in half. Yield# inside Repr.mutate could throw Cancelled after the first increment, skipping the invariant check. Both runtimes now run the body of Repr.mutate and IsoPod.mutate under _NoYield, with nested speculations detached from the cancelled parent.

What both still allow, by design. Speculation evaluates elements the sequential flow never reaches; with ParPod that opens pods the sequential program would leave closed (Legacy+ opens all of them, fearless70 a timing-dependent prefix). That is the price of .flow(mode) on mutable elements and belongs to the definition of the modes, not to either runtime. Also map{f}.size: main and Legacy+ return the known size without running f, fearless70 counts and runs it; both are internally consistent between modes, and it is a design choice.

Benchmarks

The Legacy suite (FearlessLang/benchmarks) ported to the current API in Controllers PR 33 and run by RunBenchmarks.java (Coordinator PR 160) with JMH: one fork, 2 x 3 s warm-up, 5 x 3 s measurement, average time per run of the whole program. The CPU burn is byte arithmetic (every Byte is a cached instance, so the hot loop allocates nothing; one token is a round of 255 byte multiply-adds, about 5.6 µs); an earlier version over Nat was allocation bound and showed no parallel speedup at all on this machine. Machine: 4 cores / 8 threads laptop APU, JDK 26.

DP is the parallel flow of a list, PP the same flow after limit (in Legacy+ every later stage becomes a pipeline stage; in fearless70 and main everything after limit is sequential), Seq the seqFlow. Lower is better; bars are scaled per row.

Reading them

What each design taught the other

From Legacy+ into fearless70 (now in PR 88)

  • Joining when elements are mutable. Legacy's "every terminal waits" is wrong as a rule and right for mut elements; fearless70 now distinguishes the two.
  • The methods. let (Legacy's lazy duplicator), map(ctx), actor/actorMut (a sequential gatherer), findMap, findFirst, with the ActorMatch and FlowContinuation signatures fixed so they can be called at all.
  • Not taken, and why. Pipeline parallelism after a stateful stage: it is the one shape where Legacy+ wins on the benchmarks, but a thread per stage cannot keep the ordered per-output publication and the cancellation model without a second speculation layer that passes value-or-error boxes across the stage boundary; the JDK ops on the consumer side would not see through the boxes. A bounded task budget with a sequential fallback: the common pool did not need it on these benchmarks (nested flows run their first chunk on the consumer and only park when a chunk was stolen).

From fearless70 into Legacy+ (now in PR 87)

  • Yield and the stop on a terminal error, which are trivial to add to the push design: the data-parallel source already had the flag.
  • What the port exposed. CPU-bound work on virtual threads starves the coordinating virtual threads; Legacy never noticed because it never cancelled and never needed the flusher to run before the tasks finished.
  • Not portable. Returning before the tasks finish: the flusher is the only path to the terminal, so a diverging task holds the result.

Open questions for the maintainer

  • Should map{f}.size run f? PR 88 says yes (count), PR 87 and main say no (known size).
  • Is a pipeline after a stateful stage worth a second speculation layer in PR 88, given the numbers above?
  • Do ParRepr/ParPod promise anything about elements past the decision, or only about the ones the terminal consumed?
